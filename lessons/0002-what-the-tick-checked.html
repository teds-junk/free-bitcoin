This lesson answers: What exactly did Vally run and check when it gave both models a tick?

Two models, two different entries, two green ticks. One of the entries cites a pull request that does not exist. Before you can decide what to do about that, you need to know what the tick meant. This lesson opens the two things you have only used so far: the eval file that told Vally what to do, and the folder where it wrote down what happened.

The eval file, line by line

This is the whole file you ran in lesson 1.

evals/one-request.eval.yaml
name: one-request1

defaults:
  timeout: 3m2

agent_environment:3
  skills:
    - ../skills/changelog-entry4
  files:
    - src: fixtures/notes-cli/CHANGELOG.md5
      dest: CHANGELOG.md

stimuli:6
  - name: typo-fix
    prompt: |7
      I fixed the typo in the help text for `notes add`
      (it said "tittle"). Put that in the changelog.
    graders:8
      - type: file-contains
        name: mentions-the-command
        config:
          path: CHANGELOG.md
          value: "notes add"
  1. The eval's name. Vally uses it as a folder name when it saves results.
  2. defaults holds settings that apply to every stimulus. This one is how long the agent may take before Vally stops it. The unit is required: 3m is three minutes.
  3. What the agent starts with. Everything listed here is copied into the workspace before the agent begins.
  4. A skill folder to install. The path is relative to this file.
  5. A file to copy in: src is where it is now, dest is its name in the workspace. The agent sees a file called CHANGELOG.md.
  6. The list of things to try. This file has one.
  7. The request, word for word as the agent receives it. The | means the indented lines that follow are the text.
  8. The checks to run when the agent has finished. This file has one: does CHANGELOG.md contain the text notes add?

Vally has names for the three parts, and from here on this course uses them.

Stimulus

One entry under stimuli: a request, together with the graders that check the result. The plural is stimuli.

Grader

One check, run by Vally after the agent has stopped. It reports pass or fail and a line of evidence saying what it found. Lesson 1 called this a check.

Agent environment

The skills and files copied into the workspace before the agent starts: the agent_environment part of the eval file.

The grader's type chooses one of Vally's built-in graders. file-contains reads one file in the finished workspace and passes if the file contains the text in value. The name is yours, and it is what the results show.

One more command belongs with the eval file. vally lint reads an eval file and reports mistakes in it, such as a misspelt key or a missing file, without starting an agent. It takes -e and the file's path, prints either a tick or a list of problems, and spends nothing.

Source: Vally docs, Eval Spec reference.

What a run leaves behind

Trial

One attempt at one stimulus by one model. Lesson 1's command made two trials: one stimulus, two models. From here on, a run is one vally eval command and everything it saves, and a trial is one attempt inside it.

Each vally eval command writes one folder, named with the time it started. This is everything in the folder from lesson 1:

  1. The report: a table for people, one row per stimulus, for each model.
  2. The same results for programs. Each line of the file is one record, a block of facts about one thing: one record per trial, then one summary record.
  3. Timing data for tracing tools. This course does not use it.
  4. One folder per trial, at eval name, then stimulus name, then model, then trial number.
  5. Trials are numbered from 0. With one trial per model there is only 0.
  6. The agent's own log of the session: every message, every tool it used, one event per line.
  7. A few facts about the trial: which model, when it started and ended, whether it completed.

The report is a Markdown table. Shown as a table, the row for one model reads like this (four more columns are hidden here: Environment, Skills, Tokens and Turns):

StimulusGradersPass RateDurationTool CallsVerdict
typo-fix✅ mentions-the-command 1/11/18.6s4 calls✅

The Graders column lists each grader by the name you gave it. Pass Rate is the trials that passed out of those run, here one of one. Tool Calls is how many times the agent used a tool, such as reading or editing a file. The Verdict column is the result: a trial passes only if every one of its graders passes.

results.jsonl holds the detail behind that row. It is written for programs, with each record on one very long line, so you will rarely open it. Spread out, the record for one trial looks like this:

What a trial used

A model reads and writes text in pieces called tokens, each a word or part of a word. Model services measure their work in tokens and charge for it that way. Every trial records the tokens it used, its token usage, near the end of its trajectory. This is the same record as above, the gpt-5.6-terra trial from lesson 1:

results.jsonl (the same record, inside "trajectory")
  "trajectory": {
7 fields hidden: the 46 events, final reply, paths and timings
    "metrics": {
      "tokenUsage": {
        "inputTokens": 85162,1
        "outputTokens": 615,2
        "totalTokens": 85777,3
        "cacheReadTokens": 72410,4
        "cacheWriteTokens": 12731,
        "callCount": 7,5
        "byModel": {6
          "gpt-5.6-terra": {
            "inputTokens": 85162,
            "outputTokens": 615,
            "callCount": 7
          }
        },
        "cost": {7
          "provider": "github-copilot",
          "unit": "nano-aiu",
          "amount": 53731500008
        }
      },
9 fields hidden: counts of tool calls, turns, errors and time
    }
  }
  1. Input tokens: everything the model read, added up over all its calls. That includes the request, the skill, the files the agent opened, and the conversation so far, which is read again on every call.
  2. Output tokens: everything the model wrote, the entry and its tool calls. Far fewer than it read.
  3. The two added together. This is the number in the report's Tokens column, which this lesson's table left out. With several trials of a stimulus, that column shows their median, the middle value.
  4. The part of the input read from cache: text the service had already processed earlier in the session, which it can read again more cheaply. The next line is the part it stored for later calls.
  5. How many times the agent called the model. Each call re-reads the conversation, which is why input is so much larger than output.
  6. The same counts for each model the trial used. Here there is one.
  7. What the trial cost, as GitHub Copilot reported it.
  8. The amount, in nano-AIU.
Nano-AIU and AI Credit

A nano-AIU is a billionth of an AIU, the unit Copilot reports usage in. One AIU is one GitHub AI Credit, the unit Copilot usage is billed in, and one AI Credit is $0.01.

So this trial's 5,373,150,000 nano-AIU are 5.37 AIU, about 5 cents. The claude-haiku-4.5 trial in the same run used 74,052 tokens and 2.89 AIU, about 3 cents. Across our clean re-run of lessons 1 to 15, the 213 trials with usage recorded cost about 2.2 AIU each, so a typical trial costs about 2 cents. Copilot counts usage first against your plan's monthly allowance, which differs by plan, so a trial may cost you nothing extra until that is used up.

Nothing in the next lessons depends on these numbers yet. Lesson 16 builds on them, to work out what a passing trial costs.

Sources: our run on 2026-11-10 with Vally 0.21.0; Vally docs, Trajectory Format; GitHub Docs, GitHub Copilot billing, checked 2026-11-10.

Why both models passed

Put the two halves together. The eval file's only grader asks one question: does CHANGELOG.md contain the text notes add? The evidence line confirms that is all it looked at: 'notes add' found in CHANGELOG.md. Both models wrote an entry mentioning notes add, so both passed. The invented (#42) was never examined.

That is the first thing to hold on to about any eval result. A grader objects only to what you told it to look for. A pass means "none of my graders objected". It does not mean "this is correct". A tick is exactly as informative as the graders behind it, and so far there is one grader, written before anyone had looked at what the models do.

It is tempting to fix this at once by adding a grader for invented pull request numbers. Hold off. You have seen two trials. You do not yet know whether that model always does this, or what else goes wrong on other requests. The next two lessons find out, and lesson 5 writes graders for what they turn up.

    Which file did the grader read, and what did it look for?

    Suppose a model had put its entry under the released 1.2.0 section. Would this grader have passed it?

Optional: a scripting shortcut for results.jsonl

Now that you know the shape of a record, one command prints the grading part of every record. It needs the jq tool, and it is typed in the run folder, the one that contains results.jsonl. From practice, that is the folder you moved into in step 4.

jq .gradeResult results.jsonl

jq reads the file one record at a time. .gradeResult means "print only the part named gradeResult". You get one block per trial, each with the evidence line shown above, and a final null for the summary record, which has no such part. Nothing in this course depends on this command.
