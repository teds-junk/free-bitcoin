Put a ceiling on a trial

Answer from memory before reading on.

  1. What does vally grade do, and which graders can you trust when it re-grades a saved run?
    Show answer

    It applies an eval file's current graders to trials saved in a run folder, without starting an agent. Graders that read the saved diff or trajectory are reliable. Script graders are not: the workspace is gone, so they fail on every trial.

  2. What are the two ways a grader can be wrong?
    Show answer

    It can fail correct work, or it can pass work that was not done. A grader that can never fail is the extreme case of the second.

So far: You know what a passing trial costs on each model and effort, including a model you run yourself, and what a typical trial uses.

This lesson answers: How do I fail, or stop, a trial that costs or takes too much?

Every grader so far asks whether the work is right. None asks what it took. A trial that writes the right entry after reading the same file forty times, or retrying a failing command until the time runs out, passes all of them, and you pay for every call. In lesson 16 a typical trial cost a fraction of a cent to a few cents. One that loops can cost ten times that, and a run every night multiplies whatever slips through. This lesson adds checks on what a trial used, and a limit that stops an agent before it spends too much.

A budget is a grader

A budget here is a limit on what one trial may use: tokens, time, turns, or tool calls. Written as a grader, it fails any trial that goes over. It catches two kinds of trouble. One is a trial that loops, a single run gone wrong. The other is a cost regression: an edit to the skill that makes every trial read more or take longer, which no grader of the result would notice.

Set a budget from measured trials. A budget picked by guessing is wrong in one of lesson 7's two ways: too low, and it fails good work; too high, and it can never fail, like the pattern in lesson 8. Lesson 16's runs already tell you what a typical trial uses, and a saved run is a free test of any budget you choose.

Keep a check that the work was done beside every budget. A trial that gives up after one turn is well inside every budget. A budget says "not too much"; only the other graders say "and it was right".

Budget graders

Four built-in graders compare one number from the trajectory with a max. They read the metrics block that lesson 2 showed at the end of every trial record:

GraderWhat it countsIn the record
token-budgetInput and output tokens togethertotalTokens
turn-countThe model's replies in one trialturnCount
wall-timeThe agent's working time, by the clockwallTimeMs
tool-call-countTool calls; a tools list of patterns counts only matching toolstoolCallCount

Here a turn is one reply from the model within a single trial, usually ending in a tool call or the final answer; Vally counts one each time the model finishes a reply. That is not the turn of lesson 11, which is one request in a conversation. A trial of a one-request eval has one request but several replies, and turn-count counts the replies. It is the same number as the callCount that lesson 2 showed in tokenUsage, because each reply is one call to the model: in all 103 finished trials of our lessons 15, 16 and 18 runs the two were equal, from 2 to 7. Each grader passes when the number is at or under max and fails only when it is over. This course uses the first three; tool-call-count is on the grader catalog for when you need it.

evals/changelog.eval.yaml (three budgets, under one stimulus's graders)
      - type: token-budget1
        config:
          max: 107000
      - type: turn-count
        config:
          max: 5
      - type: wall-time
        config:
          max: 14s2
  1. No name. Grader names must be unique across the whole eval file, and these three go under all five stimuli, so we leave them unnamed. Vally then names each one from its type and limit, such as token-budget max 107000.
  2. A time is written with its unit, as in defaults.timeout.

Because these graders read only the trajectory, which results.jsonl keeps in full, a re-grade with vally grade judges them exactly as a live run would. That makes them cheap to test: no agent run needed.

Over budget, a grader's score falls in proportion to the overrun, so a trial 28 tokens over scores almost 1. The verdict does not soften: the grader fails, and with no scoring block every grader must pass, so the trial fails.

Source: Vally docs, Graders: metric thresholds. The naming of unnamed graders and the duplicate-name error are from our runs on 2026-11-10 with Vally 0.21.0.

Limits that stop the agent

A budget grader judges a trial after it has finished, when the tokens are spent. To stop an agent while it is running, a stimulus takes a constraints block:

evals/changelog.eval.yaml (one stimulus, start)
  - name: typo-fix
    prompt: |
      I fixed the typo in the help text for `notes add`
      (it said "tittle"). Put that in the changelog.
    constraints:1
      max_agent_duration: 1m2
    agent_environment:
  1. Limits for this stimulus's trials. There is no eval-wide version, so each stimulus gets its own.
  2. How long the agent may work. At the limit Vally stops it, then grades whatever it had done by then, as for any finished trial. The record's endReason says agent_timeout instead of completed.

Three limits can go in the block:

  • max_agent_duration stops the agent and grades its partial work. Use it when an unfinished attempt is still worth grading, for instance to see how far the agent got.
  • max_duration is a hard limit: a trial that reaches it is stopped and counted as a failure. It does for one stimulus what defaults.timeout does for all of them. When both are set, keep max_agent_duration below the hard limit, or the hard limit ends the trial first.
  • max_turns is documented as the most turns a trial may take. The docs do not say what happens when it is reached, and we have not tested it, so this course uses the turn-count grader instead.
You want an agent that runs too long to be stopped, and what it managed to write graded as usual. Which do you add?
Right. max_agent_duration stops the agent and grades its partial work. max_duration also stops it, but fails the trial; the graders only judge after the trial ends, so they stop nothing.
max_agent_duration. It stops the agent and grades what it had done. max_duration stops it too but fails the trial, and budget graders only judge after the trial ends, so they stop nothing.
Source: Vally docs, Eval Spec reference, Constraints; read on 2026-11-10.

Set budgets from your runs

You will set budgets just above lesson 16's typical trial, test them on its saved trials, adjust them, add a time limit, and run the quick stimuli once.

The numbers below come from an earlier lesson 16 run of ours, not the one on lesson 16's page. The two are close (the run on that page has a largest median of 106,556 tokens and 12.6 seconds, against 106,673 and 13.1 here), and none of its trials went over 107,000 tokens, so with it the token budget would have passed everything first time and only the turn budget would have caught good work. Your own run will differ from both; what carries over is the method: set from your numbers, test on saved trials, widen.

What the limits caught

Our first budgets, set just above the typical trial, failed five good trials of the twenty-nine we re-graded. That is lesson 7's first way for a grader to be wrong, and the saved trials caught it, exactly as lesson 8's habit says: oracle or saved trials first, agent runs after. A typical trial is a middle value, and half of all trials are above it. terra took four, five or six turns for the same request. A budget at the median fails normal variation. The live run showed it again: a good security trial on claude-haiku-4.5 took 6 turns, which the first budget of 5 would have failed.

A budget is for the trial that runs away, at several times the usual cost, so it needs room above normal. Twice the largest typical trial still fails a loop that costs ten times as much, and passes a trial that took one turn more than usual. Re-test the budgets whenever you change the model, the effort or the skill, the same free way.

Notice what a token budget does not do. One budget holds for every model the eval runs on, and the models differ: a Haiku 5.5 trial here used about 106,000 tokens, a Haiku 4.5 trial about 75,000 and a terra trial about 61,000. A budget set for the hungriest is loose for the others. And lesson 16 showed that tokens are not price: terra used the fewest tokens and cost the most. A token budget catches a trial that loops; it does not stop you choosing an expensive model. That is what cost per passing trial is for.

The time limit did nothing in our run, which is what a limit should do on a good day. It is there for the day an agent stalls, so that a nightly run stops after a minute of waste per trial instead of the three-minute timeout, and still grades what was written.

Exercises

  1. From memory, say how a budget grader differs from a limit under constraints, in what each does to the trial and when.
    Show model answer

    A budget grader judges the finished trial and fails it if a number in its trajectory is over max; by then the cost is spent. A limit acts while the agent is working: max_agent_duration stops it and grades what it produced, and max_duration stops it and fails the trial.

  2. Our final token budget, 215000, failed no trial in any of our runs. Is it a grader that cannot fail, like lesson 8's pattern? How would you know?
    Show model answer

    No. The same grader with a lower max failed real trials in the first re-grade, so it does fail when a trial goes over. 215000 is chosen to catch a trial that uses about twice the usual or more; that none of our trials did is the expected result for good work. A grader that cannot fail is one whose condition can never be met, which is not the case here.

  3. After an edit to the skill, every trial passes its graders of the result, and the token-budget fails on every trial of one model. What does that suggest, and what do you do first?
    Show model answer

    A cost regression: the edit made that model read or write much more on every request, perhaps because the skill grew or sends it to more files. First read the trajectory of one such trial to see where the tokens went, and compare its callCount and tool calls with a trial from before the edit. That needs no new run.
