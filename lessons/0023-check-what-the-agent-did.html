So far: Your release stimulus starts where the app starts, with the tool's list already written, and a hidden test checks the entries against that list.

This lesson answers: How do I check the steps the agent took, not just the file it changed?

Inside the release tool, nobody watches the agent work. The team cares about the changelog, and also about two things the changelog cannot show. The entries must come from the list the tool wrote, not from guesses that happen to be right. And the agent must never commit or push: the release tool does that itself, after a person has looked at the result, and a commit made by the agent cannot be undone by throwing the workspace away. Lesson 22's hidden test reads only the finished file. This lesson checks the route.

Grade the path only when it matters

The default is to grade the outcome. Agents find valid routes nobody planned for, and a grader that insists on one sequence of steps fails good work: an agent that reads a file with one tool instead of another has still read it. Most of the graders in this course check results for that reason.

Check the route only when the app depends on it, and then only the step it depends on. A step can be required: the app relies on the agent working from the list, because an entry written from the file names or the history would be right by luck. A step can be forbidden: a commit, a push, a deleted file, anything with effects outside the workspace. And a route can be too long: an agent that repeats the same call costs money and time even when it gets there.

Even a route grader should be as loose as the requirement. "Read release/merged.txt" is the requirement; "used the view tool on it" is one way to meet it, and the section after next shows why that difference mattered in our runs.

Source: Anthropic, Demystifying evals for AI agents (2026-01-09), on grading what the agent produced rather than the path it took, and keeping checks on the path for steps that must or must not happen.

The tool-calls grader

Every time the agent uses a tool (reads a file, edits one, runs a shell command), the trajectory records a tool_call event. Spread out, the one where our agent read the list looks like this:

results.jsonl (one event inside one trial's trajectory)
{
  "type": "tool_call",
  "timestamp": "2026-11-10T17:47:07.708Z",
  "data": {
    "toolName": "view",1
    "toolCallId": "toolu_01SQRLn14RRSJdvNbxoFLcnk",
    "turnId": "1",
    "arguments": {2
      "path": "<workspace>/release/merged.txt"
    }
  },
  "turn": 0,
  "endTimestamp": "2026-11-10T17:47:07.713Z"
}
  1. The tool's name. The agent's runtime decides the names. In our runs: view reads a file, edit and apply_patch change one, bash runs a shell command, skill loads a skill.
  2. What the tool was given. A file tool gets a path; bash gets a command. We replaced the workspace's real location, a long temporary folder on our machine, with <workspace>.

You do not need to open that file to learn the names. The report's Tool Calls column totals them for each stimulus. Ours for the first model in lesson 22 read: view: 20, edit: 5, bash: 1.

The tool-calls grader reads these events. Every entry under required must match at least one call, and no call may match an entry under disallowed. An entry is a set of regular expressions, all of which must match the same call: name on the tool's name, command on a shell call's command, path on a file tool's path, and pattern on all the call's arguments written out as text. The expressions are unanchored, so ^view$ means exactly view and view alone would also match preview.

evals/release.eval.yaml (graders added after every-change-handled)
      - type: tool-calls
        name: reads-the-list
        config:
          required:1
            - name: ^(view|bash)$
              pattern: release/merged\.txt
      - type: tool-calls
        name: never-commits
        config:
          disallowed:2
            - name: ^bash$
              command: git (commit|push)
      - type: max-repeat3
        name: no-loop
        config:
          max: 3
      - type: skill-invocation4
        name: loads-the-skill
        config:
          required: [changelog-entry]
  1. At least one call to view or bash whose arguments mention release/merged.txt. Either tool can read a file: view directly, bash with a command such as cat.
  2. No shell command containing git commit or git push. The | inside the brackets means "or".
  3. The loop check, explained in the next section.
  4. The grader from lesson 9. The report suggested the first model rarely loaded the skill; this makes that a verdict.

When we first wrote reads-the-list it required view only. Every lesson 22 trial passed it. Then, in a run of ours for lesson 24, the first model read the list with cat through bash, and the grader failed a trial that had done exactly what the app needs. We widened it, and a re-grade of that run passed all six trials.

One more property decides how you test these graders. A grader with only a disallowed list checks for absence, so an empty trajectory passes it. As with diff-not-contains in lesson 8, the oracle cannot show such a grader failing; only a saved trial that did the forbidden thing can.

Sources: Vally docs, Grader: tool-calls; Trajectory Format. The tool names and the cat trial are from our runs on 2026-11-10 with Vally 0.21.0.

Catching loops

An agent loops when it repeats the same action without getting anywhere: rereading a file, rerunning a command that fails. Two graders look for that in the trajectory after the trial has ended. Neither stops a running agent; lesson 18's limits do that.

max-repeat fails when one action is repeated, back to back, more than max times. What counts as the same action is set by match: observation (the default) means calls that got the same result, name means calls to the same tool, and name-args the same tool with the same arguments. tools limits it to some tools, and max_cycle_period also catches an alternating pattern such as A, B, A, B. Our no-loop grader uses the defaults with max: 3: four identical results in a row fail.

loop-outcome asks a slightly different question: did the agent loop, and was that what you expected? It counts retries (four identical calls in a row are three retries) against max_acceptable_retries, and should_loop says which answer passes: false, the usual case, passes when the agent did not loop. It fits a stimulus where retrying is the very thing under test, such as a tool that fails. Lesson 24 has one, so it waits until then.

Why does never-commits need a saved trial, and not the oracle, to show it can fail?
Right. It only forbids something, and an empty trajectory does nothing forbidden. Only a real trial that ran the forbidden command can show the grader failing.
An empty trajectory commits nothing, so it passes. The oracle's baseline does nothing at all, which satisfies any grader that only forbids. Only a real trial that ran the forbidden command can show the grader failing.
Sources: Vally docs, Grader: max-repeat; Grader: loop-outcome.

What the path showed

Two of the four graders never failed a real trial: no agent committed, pushed or looped. That is the normal state for a guard. It is there for the day a model update changes the agent's habits, and you have seen that it can fail, which is what makes its passes worth anything.

The interesting result is the route each model took. Put our eight trials of the first model together, five from lesson 22 and three from this run: it loaded the skill in one, and recorded the refactor in all eight. The second model loaded it in all eight and passed all eight. The pattern points at loading, but it is not the whole story: the one trial that loaded the skill recorded the refactor anyway. One trial is far too few to say more.

For the team this changes the question. "Does the skill write good entries?" was answered in part 1. "Does the app get the skill used?" is new, and it depends on the app's own prompt, which never says "changelog entry skill", and on the model. Both are things the team controls: the app can name the skill in its prompt, or the skill's description can name this situation. Either is an edit to measure, before and after, the way lesson 15 did.

Exercises

  1. From memory: when is it worth grading the route rather than only the result, and what goes wrong when you grade it too strictly?
    Show model answer

    When the app depends on a step being taken (reading the list) or never taken (commit, push), or when a long route costs too much (loops). Too strict a route grader fails good work: our view-only requirement failed a trial that read the list with cat.

  2. The team decides the agent must change no file except CHANGELOG.md. Would you check that with tool-calls, or with a grader from part 1?
    Show model answer

    With a diff grader. A changed file is an outcome the patch records, whichever tool made the change, while a tool-calls entry would have to list every tool that can write. Every changed file starts its own diff --git a/… line in the patch, so this fails when any other file changed:

    - type: diff-not-contains
  name: only-the-changelog
  config:
    pattern: '(?m)^diff --git a/(?!CHANGELOG\.md b/)'

    (?!…) means "not followed by". We checked it on two patches: one from lesson 22, which it passed, and a copy of that patch with a deleted tools/list-merged.mjs added, which it failed. To grade a patch file you made yourself, we used vally grade with --diff-file and the file's name, in place of a run folder; lesson 25 explains that option.

  3. Your no-loop grader uses match: observation. The agent views CHANGELOG.md, edits it, and views it again. Is that a repeat?
    Show model answer

    No. The two views are not back to back, and they returned different contents, since the file changed in between. With match: name, three views in a row of different files would count as a repeat; that is why observation is the default.
