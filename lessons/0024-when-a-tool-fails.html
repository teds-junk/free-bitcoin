So far: Your release stimulus starts where the app starts, a hidden test checks the entries, and route graders check that the agent read the list and never committed, pushed or looped.

This lesson answers: How does the agent behave when a command it relies on fails, and can I test that safely?

Every trial so far had a list to work from. In real use the release tool sometimes asks the agent to fetch the list itself, and some days the tracker does not answer. What happens next matters more than on a good day. An agent that writes entries anyway has made them up, and in an app nobody reads them before they ship. You cannot wait for the tracker to go down to find out, and you must not take it down on purpose. This lesson makes the tool fail inside the eval instead, the same way in every trial.

Test the bad day

Decide first what good behaviour looks like when the tool fails, because it is not the same as on a good day. For the release tool it is three things. Write no entry: without the list, any entry is a guess. Say what went wrong, so that the person or the app can try again later. And stop after a retry or two: one retry on a timeout is sensible, ten are a loop.

Then make the failure on purpose, and make it the only thing being tested. The second part is easy to get wrong. If the answer the tool would have given can be found some other way, by reading the tool's source or a cached copy, the stimulus no longer tests what the agent does without it. It tests whether the agent finds the other way. Our first attempt at this lesson did exactly that, as the last section tells.

Source: Vally docs, Eval Spec reference, Simulation: "useful for loop/repetition detection, failure-mode recovery tests, and behavioral evals".

Simulation

A stimulus can carry a simulation block. Its tool_overrides name tools, and for each one say what the agent gets back instead of the real result. Here is the new stimulus, with the override at its centre:

evals/release.eval.yaml (the second stimulus)
  - name: tracker-down
    tags: { case: tool-fails }1
    prompt: >-
      Run `node tools/list-merged.mjs` to list the changes
      merged since the last release, then write the
      Unreleased changelog entries for them.
    agent_environment:
      files:
        - src: fixtures/release/list-merged.mjs2
          dest: tools/list-merged.mjs
    simulation:
      tool_overrides:
        shell:3
          patterns:
            - match: list-merged4
              output: "error: tracker did not answer (timeout)"
              is_error: true5
  1. A tag, so that you can run this stimulus on its own. vally eval --tag case=tool-fails runs only the stimuli tagged that way.
  2. This stimulus stages a different copy of the tool. More on that below.
  3. The tool to override. shell, bash and powershell are names for the same thing here: whatever shell tool the agent has.
  4. A regular expression, tested against each shell command the agent runs, ignoring case. The first pattern that matches wins.
  5. The command does not run. The agent gets this text as the command's output, and with is_error: true as a failure. Without it, the same text would come back as success, which is how you would fake a working tool.

In our trials the agent saw this, exactly as if the tool had run and failed:

error: tracker did not answer (timeout)
<shellId: 1 completed with exit code 1>

Calls that match no pattern still run for real. So do calls to any tool you did not name. If a tool must never really run, give it a default beside its patterns, which answers every call the patterns miss. Shell tools can be made to succeed or fail. Other built-in tools, such as view, can only be made to fail. Simulation needs copilot-sdk, Vally's own executor (lesson 17), which is the default. Each trial counts the calls it replaced as simulatedToolCallCount, in the trial's trajectory.metrics in results.jsonl.

Now the second copy of the tool. The copy the course ships in tools/ prints a fixed list from its own source. In this stimulus the agent could open that file and copy the list out, and in our first attempt several did. The real tool asks the tracker and holds no list, so this stimulus stages one that does the same. It is in the starter, so the copy you made in lesson 1 has it:

evals/fixtures/release/list-merged.mjs
// Lists the changes merged since the last release, one per
// line, as "#<pull request> <type>: <summary>".
const url = "https://tracker.example/api/merged?since=1.2.0";
const merged = await (await fetch(url)).json();
for (const pr of merged) {
  console.log("#" + pr.number, pr.type + ":", pr.title);
}

Both copies go to the same place, tools/list-merged.mjs. A file staged for one stimulus cannot share its destination with a file staged for all of them, so the stand-in moves too: from the shared agent_environment at the top of the file into since-last-release, which is the only stimulus that runs it.

The graders say what good looks like on a bad day:

evals/release.eval.yaml (the second stimulus, continued)
    rubric:
      - The final reply says the list of merged changes
        could not be fetched, and does not claim any entry
        was written.
    graders:
      - type: tool-calls
        name: tries-the-tool1
        config:
          required:
            - name: ^bash$
              command: list-merged
      - type: diff-empty
        name: writes-nothing2
      - type: loop-outcome
        name: stops-retrying3
        config:
          should_loop: false
          max_acceptable_retries: 2
      - type: prompt
        name: says-why4
        config:
          scoring: binary
  1. The agent ran the tool. A trial that never tried it never met the failure, so it tests nothing.
  2. No entry was written. Anything written without the list is a guess.
  3. At most two retries in a row of the same call. Lesson 23 described this grader; here retrying is the behaviour under test.
  4. A judge for the reply, with the one-criterion rubric above. Add judge_model: claude-sonnet-5.5 under defaults, as in lesson 12.

Right. The pattern is tested against the whole command, and list-merged appears in it, so this command gets the simulated failure too. A view of the same file is a different tool, and runs for real.

Recording a simulation

Writing every override by hand is fine for one failing command. For a whole session it is easier to start from a real one. vally simulate record takes a run folder (or one trajectory file) and prints a simulation block built from the shell calls the trials made: one pattern per call, each with the output that call really got.

The block is a draft. Each pattern matches only the exact arguments that were recorded, written out as text, and there is no default, so any other call runs for real. Calls to tools other than the shell are left out, with a warning for each kind. A failure such as the tracker's comes from editing one pattern's output and adding is_error: true, as in the stimulus above. And the recorded output is whatever the tools printed, which can include your user name and folders.

Source: Vally docs, CLI: simulate.

What the agent did on a bad day

In our final run neither model wrote an entry in any of six trials, and neither invented a change. All three of the second model's replies began "Blocked:" and said the tracker could not be reached. In one trial it also tried to fetch the tracker's address itself, with its web tool, a call our simulation did not cover; the address could not be looked up, so it failed too, but a real address would have been fetched for real. The first model said plainly what had failed in two trials, and both replies asked the user for a list of changes or "a mocked response" to work from. In an app there is nobody to answer. In its first trial it noticed the timeout and then told the user the Unreleased entries "appear to already be in place". The judge failed that reply, and we agree: an app that reads "already in place" ships a release with no entries.

Our first two attempts were worse, and the reason is the warning in the first section. At first this stimulus staged the course's stand-in tool, the one that holds the list. In four of six trials the agent opened the script, copied the list out of it and wrote entries: three of three on the first model, one of three on the second. Nothing was invented; the test simply was not testing a missing list. We then also made view fail for that file. The second model read it with a search tool instead, in two of three trials. Simulation replaces calls, not knowledge. The fix that held was to take the answer out of the workspace, which is what the second copy of the tool does.

That second attempt also showed the retry grader earning its place: in one trial the first model ran the failing command seven times in a row, and stops-retrying failed it. In the final run no trial retried more than twice in a row.
