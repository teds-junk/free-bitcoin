Keep graders out of the agent's reach

So far: You can turn a failure mode into a pattern grader and count how often it happens before and after an edit to the skill.

This lesson answers: Where can I put a grading script so the agent cannot read or change it?

Patterns have a limit. A pattern can say "the patch contains an entry citing pull request 60". It cannot say "and that entry sits under Fixed, inside Unreleased, and not inside a version that has already shipped". Position in a file is structure, and structure needs a few lines of code that read the file. The moment a grader is a script, a new question appears: a script is a file, the agent works in a folder full of files, and an agent that can read its own exam, or edit it, tells you nothing.

Why the agent must not see the grader

An agent can read and edit everything in its workspace. If the grading script were there, three things could happen. The agent could read it and learn exactly what is being looked for. It could edit it so that it always passes. Or, most likely, it could simply be distracted by an unexpected file and start "fixing" it.

This is not a theoretical worry. A benchmark is a public set of tasks with graders, used to compare agents. In April 2026, researchers at Berkeley took eight well-known ones and scored between 73% and 100% on them with agents that solved none of the tasks, for example by reading answers the graders had left where an agent could reach them. In June 2026, the makers of the Cursor editor reported that in 63% of one model's passing runs on a coding benchmark, the agent had found the published fix and copied it instead of working it out.

Your changelog skill does not need a security review. It needs two plain rules. Keep grading scripts and expected answers where the agent cannot see them. And never let a grader depend on a file the agent could have altered in order to pass.

Sources: Berkeley RDI, How we broke top AI agent benchmarks, April 2026; Cursor, Reward hacking on coding benchmarks, 2026-06-25 (reported by the vendor, one model).

What goes into the workspace

Lesson 2 defined the agent environment: the skills and files copied into the workspace before the agent starts. Two details matter now.

First, a skill is copied as a whole folder. Whatever is inside the skill's folder goes into the workspace, not only SKILL.md. Second, files listed under files arrive under the name you give as dest.

You can see this for yourself. Adding --workspace and a folder name to vally eval tells Vally to keep each trial's workspace in that folder when the trial ends, where it would normally delete it. The command find kept -type f then lists every file under a folder named kept. For the one-request eval file and one model, this is everything that was kept:

kept/main/typo-fix/CHANGELOG.md
kept/main/typo-fix/changelog-entry/SKILL.md

The path is the folder you named, then a folder Vally calls main, then the stimulus name. Inside is what the agent had: the changelog, as it left it, and the skill folder.

--workspace works with one model at a time. The kept path has no model name in it, so with several models Vally stops before running anything and reports workspace-collision.

Keep eval files outside the skill folder

Because the whole skill folder is copied, anything you store inside it is handed to the agent: eval files, graders, expected answers. This course keeps evals/ beside skills/, never inside a skill.

Sources: Vally docs, Eval Spec reference; the listing and the collision are from our runs on 2026-11-10 with Vally 0.21.0.

What is added only for grading

Grading environment

Files that Vally adds after the agent has stopped, to a copy of the finished workspace that only graders use. The copy is thrown away when grading ends. It is the grading_environment part of a stimulus.

The grader that runs a script is called program. It runs one program inside the grading copy, and the program tells Vally the verdict by printing it. This course calls a program grader that runs a script a script grader. Here is a stimulus with a grading environment and a script grader.

evals/changelog.eval.yaml (a new stimulus)
  - name: two-changes
9 lines hidden: the prompt and the starting changelog
    grading_environment:1
      files:
        - src: grading/check-entry.mjs2
          dest: .vally-grading/check-entry.mjs3
    graders:
      - type: program4
        name: two-entries-in-place
        config:
          program: node
          args:5
            - .vally-grading/check-entry.mjs
            - Added=60
            - Fixed=60
  1. Files for graders only. It is written like the files part of the agent environment.
  2. Where the script is now: in evals/grading, which no agent environment copies.
  3. Where it goes in the grading copy. A folder starting with a dot keeps it apart from the agent's files.
  4. Run a program in the grading copy and take the verdict from what it prints. The program is node, which runs JavaScript files, and the script is one.
  5. The command's arguments: the script to run, then what to look for.

The script ships with the starter folder, in plain JavaScript with nothing to install. Its opening comment says what it checks, and its last few lines say how it reports.

evals/grading/check-entry.mjs
// Checks the finished CHANGELOG.md.
// Each argument is Category=number. The Unreleased section
// must have an entry under that category that cites that
// pull request. Prints one result: pass or fail, and why.
31 lines hidden: the code that reads the changelog
function report(passed, evidence) {
  console.log(JSON.stringify({1
    name: "check-entry",
    kind: "code",2
    passed,3
    score: passed ? 1 : 0,4
    evidence,5
  }));
  process.exit(0);6
}
  1. Print the result as one line of JSON. JSON is a common way of writing data as text: names and values inside braces. Each record in results.jsonl, from lesson 2, is written the same way.
  2. Says that code made this check. Vally needs all five fields, from name to evidence.
  3. The verdict: true for a pass, false for a fail.
  4. 1 for a pass, 0 for a fail.
  5. A sentence saying what the script found, such as no entry citing #60 under Fixed. It appears in the results as the grader's evidence, where a pattern grader's evidence appears.
  6. Every program ends by reporting a number, its exit code, and 0 means "no problem". This script exits with 0 whether the entry is there or not, because the verdict is in what it printed. A different exit code would mean the script itself had broken.

So Added=60 and Fixed=60 mean: under Unreleased there must be an entry under Added that cites (#60), and one under Fixed that cites (#60). An entry in a released version does not count, and the heading must be written exactly as ## [Unreleased].

The starter has a second stimulus ready as well, after-release, for the changelog with no Unreleased section. Its grader is named entry-in-new-unreleased, and it asks the script for Added=58. Both stimuli are in evals/snippets/lesson-6-stimuli.yaml, for you to paste in.

Two things about script graders are worth knowing in advance. vally lint refuses a grading file whose source the agent could see, with the error grading-file-src-agent-visible. And if a script prints a result with a field missing, Vally fails the trial with Grader output did not match schema. That is a mistake in the script, not in the agent's work.

The other script grader

Vally has a second grader that runs a script, run-command, which passes when the script exits with 0. It is simpler to write and tells you less: when it fails, the evidence is only Expected exit code 0, got 1, and you have to read the patch to find out why. This course uses program so the results say why.

You move check-entry.mjs into skills/changelog-entry/ to keep things tidy. What happens?

What the script caught, and what it missed

Three things happened in our runs that are worth dwelling on.

The heading without brackets appeared on both models this time. In lesson 4 only one model wrote ## Unreleased. One trial per model shows that a failure can happen; it does not show which model is prone to it. After the new rule, the second model wrote the heading correctly. The first model's trial ended in ERROR, so for that model this run cannot say.

Then the surprise, and it is not a happy one. In the second run the script passed every two-changes trial, and one of them was wrong. This is its patch, with the first five lines and one long line shortened:

 ### Added
 - Add `notes list --tag` to filter by tag (#41)
+- Add `notes list --json` to output as JSON (#60)
 
-## [1.2.0] - 2026-09-14
+### Fixed
+- Fix pagination bug where page 2 repeated … (#60)
 
 ### Added
 - Add `notes export` for a single-file backup (#37)

The agent wrote its Fixed entry where the heading of version 1.2.0 had been, and deleted that heading. Version 1.2.0 has been released, and its entries now sit under Unreleased, as if they had never shipped. The script finds the Unreleased section and reads down to the next version heading. With 1.2.0's heading gone, the next one was further down, so the script found every entry it wanted and passed.

That is a sixth failure mode, and the grader hid it. A grader that passes a wrong answer is worse than none, because its tick tells you to stop looking. The skill already forbids this ("Leave released versions alone"), so the gap is in the grader, not the skill. Exercise 3 below closes it. Lessons 7 and 8 are about catching graders like this one before they mislead you.

The third thing is quieter. In lesson 5 the first model filed the security fix under Fixed in one of three trials. In these two runs, with the same rule in the skill, it filed it under Security every time. Nothing was changed to cause that. It is the run-to-run variation from lesson 3, and a reminder that two or three trials are a glimpse, not a measurement.

Exercises

  1. From memory, say what the agent environment and the grading environment each add, and when.
    Show model answer

    The agent environment copies skills and files into the workspace before the agent starts; the agent can read and edit all of it. The grading environment adds files to a copy of the finished workspace after the agent has stopped; only graders use that copy, and it is thrown away afterwards.

  2. A teammate stores expected answers in skills/their-skill/evals/answers.json. Explain the problem in one sentence and give the fix.
    Show model answer

    The whole skill folder is copied into the agent's workspace, so the agent can read the answers; move the evals folder out of the skill folder, and bring answers.json in through grading_environment if a grader needs it.

  3. Write a second grader for two-changes that fails the trial shown above: one that fails whenever the agent deletes a version heading. Use a pattern grader from lesson 5.
    Show model answer 
          - type: diff-not-contains
        name: keeps-released-versions
        config:
          pattern: '(?m)^-## \['

    In a patch, a deleted line starts with a minus sign, and every version heading starts with ## [. So the pattern matches a deleted version heading anywhere in the patch, and the grader fails. We tested it on our two two-changes trials from the second run: it failed the one above and passed the other.
