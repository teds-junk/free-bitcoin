  1. What is the difference between a stimulus marked FAIL and one marked ERROR?
    Show answer

    FAIL means every trial finished and none passed its graders. ERROR means at least one trial did not finish, so there was nothing to judge; run it again.

  2. A trial passes all its graders. What does that tell you, and what does it not?
    Show answer

    It tells you none of the graders objected. It does not tell you the result is correct: a grader looks only at what it was told to look for.

This lesson answers: What else goes wrong when the requests get messier?

You know about one problem because you happened to look. The request you have been using is one of the tidier things a person might ask for. Real requests mention changes users will never see, bundle two changes together, describe a fix by how it was coded, or arrive just after a release. Before writing a single grader, you need to see what the skill does with those, and the only way to see is to read.

Why reading comes first

The natural instinct is to sit down and list what a good changelog entry looks like, then write graders for the list. The trouble is that the list comes from your imagination, and the failures come from the models. In lesson 1 nobody would have thought to write "must not invent a pull request number" until a model did it.

Practitioners who do this for a living put it as a rule: "Write evaluators for errors you discover, not errors you imagine." Evaluators is their word for graders. The process they recommend is plain. Run realistic requests, read what came back, write a short note on each, and group the notes. They call it error analysis.

Failure mode

A named way in which the skill's output goes wrong, seen in at least one real trial. "Records a change users cannot see" is a failure mode. "Trial 3 looked odd" is not yet one.

Reading also does something a list cannot: it makes you decide what you want. Is a security fix filed under "Fixed" wrong? You will not have an opinion until you see it, and once you do, that opinion is a rule the skill is missing. Researchers who studied this found that people's criteria shift as they read outputs, so criteria written beforehand are incomplete.

How many runs are enough? The same practitioners suggest reading at least a hundred for a real product, and stopping when new ones stop showing you anything new. This lesson reads twelve. That is enough to find the main failure modes of a five-line skill, and too few to be sure you have found them all.

Sources: Husain and Shankar, AI Evals FAQ, reissued 2026-09-18, which says "traces" where Vally says trajectories; Shankar et al., Who Validates the Validators?, 2024, on criteria shifting as outputs are read.

Six ordinary requests

The starter folder has a second eval file with six stimuli. One eval file can hold as many as you like, and Vally runs each of them on each model.

evals/six-requests.eval.yaml
name: six

defaults:
  timeout: 3m

agent_environment:
  skills:
    - ../skills/changelog-entry

stimuli:
  - name: typo-fix1
    prompt: |
      I fixed the typo in the help text for `notes add`
      (it said "tittle"). Put that in the changelog.
    agent_environment:2
      files:
        - src: fixtures/notes-cli/CHANGELOG.md
          dest: CHANGELOG.md
43 lines hidden: four more stimuli
  - name: after-release3
    prompt: |
      PR 58 just landed: `notes add` now accepts
      `--from-clipboard` to create a note from whatever
      is on the clipboard. Add it to the changelog.
    agent_environment:
      files:
        - src: fixtures/just-released/CHANGELOG.md4
          dest: CHANGELOG.md
  1. The request you already know, so this run can be compared with lesson 3.
  2. A stimulus can have its own agent_environment. Here each stimulus names the changelog it starts from. The skill is listed once, at the top, for all of them.
  3. There are no graders anywhere in this file. That is allowed.
  4. This stimulus starts from a different changelog: one where version 1.3.0 has just been released, so there is no "Unreleased" section yet.

The four hidden stimuli are a refactor (a tidying of the code that changes nothing for users), one pull request containing two changes, a security fix, and a fix described by how it was coded. Each one leaves the skill something to decide that it does not mention.

To judge the results you need one fact about the project. Its changelog follows a public format called Keep a Changelog. That format has six categories, in this order: Added, Changed, Deprecated, Removed, Fixed and Security. It writes the heading for unshipped changes as ## [Unreleased], with the square brackets. The skill mentions none of this.

Because the purpose of this run is to read, the command adds --skip-grade. With it, Vally runs the agents and saves everything as usual, and skips grading. This file has no graders, so the option changes nothing yet; it states the purpose, and it is what you would use on a file that has some. The summary still prints ticks. With --skip-grade a tick means only that the trial finished.

Sources: Vally docs, CLI: eval; Keep a Changelog 1.1.0. The meaning of the ticks is from our run on 2026-11-10 with Vally 0.21.0.

Where the failures come from

Look at where our five failure modes come from. In every one, the skill left a question open: what to do without a pull request number, which changes count, which categories exist, what "written for people who use the tool" rules out, what a new heading looks like. The models did not disobey the skill. They each filled a gap, and they filled it differently. That is good news, because gaps in a skill are yours to close.

Your list will not match ours exactly, and some entries on it will be matters of taste. Deciding which ones you care about is part of the work. The project's format settles two of ours: a security fix has its own category, and the heading has square brackets.

    Such graders check for failures you imagined, and the real failures come from what the models do with gaps in the skill, which you cannot predict. Reading also changes what you consider wrong, so criteria written beforehand are incomplete.
