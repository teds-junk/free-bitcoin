  1. What two tests does vally oracle run on a grader, and what does it cost?
    Show answer

    With the golden patch applied, a healthy grader passes. With --no-golden-input, on the untouched baseline, a healthy grader fails. It starts no agent, so it costs nothing.

  2. What does a token-budget grader do, and how did lesson 18 choose its max?
    Show answer

    It reads the trial's token count from the trajectory and fails the trial when the count is above max. Lesson 18 first set it just above the typical trial, found in a free re-grade that this failed good work, and raised it to about twice the largest typical trial: 215000 in our run.

So far: You have eval files for single requests, a conversation, loading and wording, with tested graders, a measured judge and a way to tell a real change from luck. You know what a passing trial costs, budgets guard each trial, a pairwise judge can say whether an edit made things worse, and you have four questions for a run that goes wrong.

This lesson answers: How do I make this a routine that I and a teammate can repeat?

Everything you have built works when you remember to run it, in the right order, with the right flags. That is not a routine, and it will not survive a busy week or a new teammate. The skill will be edited again. The models under it will change without telling you, and so will their prices. What keeps it working is making the right check the easy one: one short command after every edit, a longer one before anything is shared, and a page that says what your team agreed. This lesson, the last of part 1, builds those three things.

Cheapest check first

You now have five ways to check the skill, and they differ enormously in cost. Use the cheapest one that can answer the question you actually have.

CheckAnswersWhen
vally lintIs the eval file well formed?After editing an eval file
vally oracleDo the graders pass a correct answer and fail an empty one?After writing or changing a grader
vally gradeWhat do today's graders and budgets say about trials already saved?After changing a pattern grader, a budget or a rubric. Script graders need the oracle instead
Quick suiteDid my edit break anything code can check, or push a trial over budget?After every edit to the skill
Full suiteDoes everything still hold, loading and wording included?Before sharing the skill, and when a model changes

Three more checks sit outside this order because they answer one-off questions. The with-and-without experiment from lesson 10 is worth repeating after a large rewrite. A before-and-after experiment, as in lesson 15, followed by vally compare from lesson 19, tells you whether an edit really helped or made things worse; the comparison starts no agent but spends about two judge calls per pair of trials. And lesson 16's cost per passing trial is the check to run before you move the suites to a different model or reasoning effort.

For a team, the commands are the easy part. What drifts is agreement: what deserves a grader, where grading files live, how a result is reported, what a run may cost. Write those down in one page while they are fresh. A page that people can disagree with is how the agreement gets better.

Source: Husain and Shankar, AI Evals FAQ, reissued 2026-09-18, on running cheap exact checks on every change and judges less often.

Tags, suites and exit codes

A tag is a label you put on a stimulus: a name and a value, on a tags line. The name tier and the value quick are ours. Any words will do.

evals/changelog.eval.yaml (the start of one stimulus)
  - name: typo-fix
    tags: { tier: quick }
Suite

A named group of stimuli: a list of eval files, optionally narrowed to stimuli with a given tag. Suites are defined in a file named .vally.yaml in the folder you run Vally from.

.vally.yaml
suites:
  quick:1
    description: Code graders and budgets, one trial.
    evals:2
      - evals/changelog.eval.yaml
    filter: { tier: quick }3
  full:
    description: Everything, with loading and the judge.
    evals:4
      - evals/changelog.eval.yaml
      - evals/conversation.eval.yaml
      - evals/loading.eval.yaml
      - evals/wording.eval.yaml
  1. The suite's name, which is what you type on the command line.
  2. The eval files it draws on, relative to this file.
  3. Only stimuli tagged tier: quick are run.
  4. No filter, so every stimulus in these four files is run.

To run a suite, give vally eval the option --suite and the suite's name in place of -e and a file. Everything else works as before.

A suite names stimuli; it adds no graders of its own. The five quick stimuli are the ones you gave budgets in lesson 18, so the quick suite carries them: every trial is checked against 215000 tokens, 10 turns and 30 seconds, and lesson 18's max_agent_duration: 1m stops the agent after a minute and grades what it had done. Behind that, timeout: 3m under the file's defaults is the hard limit on each trial, which ends it in ERROR (lesson 20). A trial over a budget fails its stimulus like a trial whose entry is wrong. That is what makes the quick suite a cost check as well as a quality check.

The last piece is how a command reports failure to whatever ran it. As lesson 6 said, every command ends with an exit code, a number: 0 means it succeeded, anything else means it did not. Scripts and automated checks read that number. In a terminal you can print the last command's exit code with echo $?.

By default, vally eval exits with 0 even when stimuli fail, because the run itself completed. Adding --require-pass changes that: any failing stimulus makes the exit code 1, whichever grader failed it, budgets included. A run that hit an ERROR exits with 1 either way. vally grade accepts the same option.

One kind of failure no grader sees: an edit that makes the entries a little worse while every pattern still matches. That is lesson 19's pairwise judge. vally compare with --fail-on-regression exits 1 when the change under test scored worse than the baseline, with the whole range below zero. In lesson 19 we ran it with the two roles swapped, so that the before skill was the change under test. We ran that twice. In one of our two runs the whole range lay below zero:

vally compare \
  --baseline haiku-after \
  --treatment haiku-before \
  --judge-model claude-sonnet-5.5 \
  --fail-on-regression
  Mean score: -0.49 [95% CI -0.90, -0.07]
    (+ = treatment better)

❌ Regression: 'haiku-before' scored
   significantly worse than baseline.

That output is from the earlier of our two runs in lesson 19, wrapped to fit, and the command exited with 1. In the later run the range reached +0.02 and it exited 0: a range that ends near zero can land on either side of it. We do not run it again here: it needs a before-and-after experiment and spends about eighteen judge calls each time. So it belongs before you rely on an edit you have measured with an experiment, not after every edit. Remember too what lesson 19 found: it gates on the judged score alone. A rise in tokens is the budgets' job.

You run the quick suite without --require-pass. One trial goes over its token budget; every other grader passes and nothing errors. What is the exit code?
Right. The budget fails that stimulus, but without --require-pass a failing verdict still exits with 0. That is why an automated check must add the option.
Zero, because the run completed. The budget does fail the stimulus, but without --require-pass a failing verdict does not change the exit code; only an ERROR does. An automated check has to add the option.

Two suites and a conventions page

You will tag five stimuli, define the two suites, run the quick one so that it fails loudly, see a failing exit code for a wrong entry and for an over-budget trial without spending anything, run the full suite once, and write your conventions.

A routine anyone can run

  1. Goal: tag the stimuli that code can check. This edits one file. Open a terminal in practice. In evals/changelog.eval.yaml, add the line tags: { tier: quick } under the name of each of the five stimuli, as shown above.
  2. Goal: define the two suites. This creates one file. Create a file named .vally.yaml in practice with the thirteen lines shown above. The name begins with a dot.
  3. Goal: catch mistakes before spending anything. 
    vally lint -e evals/changelog.eval.yaml

    You should see: the usual one warning, scoring-defaults-applied, and no errors.

  4. Goal: run the quick suite so that a failure is an error. This spends ten agent runs. 
    vally eval --suite quick \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --workers 2 --require-pass \
  --output-dir results/lesson-21-quick
      eval       claude-haiku-4.5  gpt-5.6-terra
  changelog  ✓ 5/5             ✓ 5/5

    You should see: your summary. Ours is above: every stimulus passed on both models, budgets included.

  5. Goal: read the exit code of that run. 
    echo $?
    0

    You should see: 0 if every stimulus passed, as ours did, and 1 if any failed.

  6. Goal: see a wrong entry fail loudly, without spending anything. Your "before" run from lesson 5 is full of failures, and its stimuli use only diff graders and budgets, which re-grade correctly. Re-grade it with --require-pass. Use your folder's name. 
    cd results/lesson-5-before/2026-11-10T14-55-35-995Z
    vally grade -e ../../../evals/changelog.eval.yaml \
  --run-dir . --require-pass < results.jsonl
    echo $?

    You should see: the failing blocks from lesson 8, each now with the budgets among its graders, then 1. One of ours, wrapped to fit:

    ❌ refactor (3/4 graders passed, 1 failed)
  ✗ [adds-nothing] Workspace diff is not
    empty — the stimulus changed the workspace

Score: 75.0% | FAILED

    Every budget passed every one of those eighteen trials; only the graders of the result failed.

  7. Goal: see an over-budget trial fail loudly, for free. This edits one file for a moment. In evals/changelog.eval.yaml, in the typo-fix stimulus, change the token-budget's max from 215000 to 70000, below what these trials used. Then run the same vally grade command again, and echo $?.

    You should see: 1 again, and the typo-fix trials of your first model, which passed every grader in the previous step, now failing on the budget alone. Ours:

    ❌ typo-fix (4/5 graders passed, 1 failed)
  ✗ [token-budget max 70000] 74052 tokens
    exceeds max of 70000

Score: 98.8% | FAILED

    Two more blocks like it followed, at 74,161 and 74,202 tokens. A trial that did the work and cost too much is a failing verdict like any other.

    Why 98.8% and still FAILED: the score is the plain average of the five graders' scores (lesson 14). Four passed and score 1. A budget grader over its max scores less in proportion to the overrun (lesson 18): 1 − (74052 − 70000) ÷ 70000, about 0.94. The average of 1, 1, 1, 1 and 0.94 is 98.8%. With no scoring block the score decides nothing; every grader must pass, and one did not.

  8. Goal: undo the experiment and go back. This edits one file. Change the max back to 215000, then return to practice: 
    cd ../../..
  9. Goal: run everything once. This spends thirty agent runs and six judge calls, and takes several minutes. 
    vally eval --suite full \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --workers 2 --require-pass \
  --output-dir results/lesson-21-full
    conversation · claude-haiku-4.5
  FAIL  three-requests · 4/5 graders · 17.5s
   ✘ third-no-made-up-number  Pattern …
     found in workspace diff

loading · gpt-5.6-terra
  ERROR  skip-release-notes
   Session disconnected while waiting …

  eval          claude-haiku-4.5  gpt-5.6-terra
  changelog     ✓ 5/5             ✓ 5/5
  conversation  ✘ 0/1             ✓ 1/1
  loading       ✓ 6/6             ✘ 5/6
  wording       ✓ 3/3             ✓ 3/3

    You should see: one row per eval file, one trial each, and a block above the table for any stimulus that did not pass. Ours is above, and it shows two different kinds of trouble. One loading trial on the second model ended in ERROR because the session dropped. That is lesson 20's second question, "did it complete?", and the answer was no, so it says nothing about the skill: run it again, or leave that trial out and say so when you report the result. The other is a real FAIL. On claude-haiku-4.5, the conversation's third entry, for the notes export fix, cited (#65): the number of the internal rename from the second request. That is the leak lesson 11 found and added a rule against, and its grader caught it. Every other stimulus passed on both models, budgets and judge included. Either problem alone makes the command exit with 1, and ours did.

  10. Goal: write down what you have agreed with yourself. This creates one file. Create CONVENTIONS.md in practice. Give it these ten headings, and one or two sentences under each, in your own words: what earns a grader; code first, judge second; where files live; before trusting a grader; before trusting a judge; what we run and when; how we report a result; what a run may cost; when a run goes wrong; models and dates. The last matters because models and their prices change: a result means little without knowing which model produced it, and when.
    Show our conventions
    1. What earns a grader. A failure we have seen in a real trial. One grader per failure mode, named after it.
    2. Code first, judge second. A judge only for what code cannot decide, with one yes-or-no criterion.
    3. Where files live. evals/ beside skills/, never inside a skill. Grading scripts in evals/grading, brought in through the grading environment.
    4. Before trusting a grader. The oracle, with and without the golden patch. A grader that checks for absence must also fail a saved trial known to be bad. A new budget is re-graded against saved trials and must pass all the good ones.
    5. Before trusting a judge. Our own labels first. TPR and TNR (lesson 13: how often the judge passes what we passed, and fails what we failed) reported with the number of labels. Label again when the rubric or the judge model changes.
    6. What we run and when. The quick suite with --require-pass after every edit to the skill. The full suite before sharing and when a model changes. A before-and-after experiment and vally compare --fail-on-regression before relying on an edit. With-and-without after a large rewrite.
    7. How we report a result. Counts, per model, with cost per passing trial. "These trials cannot tell" when the ranges overlap.
    8. What a run may cost. Budgets at about twice the largest typical trial: 215000 tokens, 10 turns, 30 seconds, and a 1-minute limit on the agent. Re-tested for free whenever the skill, the model or the effort changes. Cost per passing trial compared before switching models, with the judge's calls counted on top.
    9. When a run goes wrong. The four questions in order: is the eval valid, did it complete, why was the result unexpected, does the fix work. Read what the run saved before running anything again; an ERROR is re-run or left out and said so, never counted as a failure of the skill.
    10. Models and dates. claude-haiku-4.5 and gpt-5.6-terra, judged by claude-sonnet-5.5, checked on 2026-11-10, at $0.01 per AIU.

Where the skill stands

Compare the last table with where you started. In lesson 1 this skill was five lines that one model answered by inventing a pull request number, and a tick that hid it. In lesson 5 a single stimulus-and-model pair out of six passed. Now the suites cover a conversation, a loading test with near-misses, a judged quality that no pattern can see, and budgets on every quick stimulus. In our last run every stimulus passed on both models except two: one trial whose session dropped, and one conversation on claude-haiku-4.5 in which a number from an earlier request leaked into a later entry. Lesson 11's rule did not make that leak impossible; the grader lesson 11 added is what caught it. Every rule in the skill is there because a trial showed it was needed, and every grader is there because a failure was seen.

Now say what it costs. In our run the quick suite's ten trials cost 23.81 AIU, about 24 cents an edit: 9.62 AIU on claude-haiku-4.5 and 14.19 on gpt-5.6-terra, from 1.63 to 3.40 AIU a trial. The full suite's 29 finished trials cost 64.03 AIU, about 64 cents, an average of 2.21 AIU a trial, close to the 2.2 AIU that lesson 16 used for its estimates; its six judge calls are on top. None of these trials came near the token budget: the largest quick trial used 91,454 tokens against 215000.

Those numbers are for the course's pair of models. Lesson 16 found claude-haiku-5.5 at low effort passing all 15 of its trials on the same five quick stimuli at 0.21 AIU per passing trial, so a quick suite on that one variant would cost about 1 AIU an edit, a cent. Our conventions say how to make that move: compare cost per passing trial, re-test the budgets on its saved trials, and run the full suite on it first, since the judged wording stimuli are where models differed.

Keep one caution from lesson 15 as you close part 1. That last table is one trial per stimulus. Our own run shows why that matters: the conversation passed all six of lesson 11's runs after its fix, and failed here. One trial says what can pass, not what always will. The suites are how you find out when that changes.

One step is left for you. Teams often have a service run a check like the quick suite automatically, every time someone proposes a change to the code. We could not run that for this course, because it needs a project of your own hosted on such a service. Exercises

  1. From memory, list the five checks in order of cost, and say when you would use each.
    Show model answer

    Lint, after editing an eval file. The oracle, after writing or changing a grader. A re-grade of a saved run, after changing a grader, a budget or a rubric. The quick suite, after every edit to the skill. The full suite, before sharing the skill and when a model changes.

  2. Name the three ways a command in your routine can fail loudly, and the command and option for each.
    Show model answer

    A failing verdict and an over-budget trial both fail a stimulus, so vally eval (or vally grade) with --require-pass exits 1 for either. A regression in judged quality makes vally compare with --fail-on-regression exit 1. An ERROR exits 1 from any of them, with or without the option.

  3. After an edit, the quick suite exits 0, but the summary shows every trial using about a third more tokens than before, still under the budget. Which of your three gates caught it, and what would you do?
    Show model answer

    None of them. The budget sits at about twice the typical trial, so a third more passes, and --fail-on-regression looks only at the judged score. Read the metric lines: lesson 19 prints the token change with its range, and the cost calculator gives cost per passing trial. If the rise is real and not worth it, change the edit; if you accept it, re-test the budgets on the new trials as lesson 18 did.

  4. A model you depend on is replaced by a newer one. Write, in order, what you would run, and what would make you edit the skill.
    Show model answer

    Put the new model name in the commands and the experiment files. Re-grade saved trials of the new model against the budgets once you have some, since its token counts will differ. Run the full suite on it, and price it with cost per passing trial. Run the with-and-without experiment, since a newer model may no longer need some rules, or may react badly to one. Read the patches of anything that fails before changing a rule, and measure any edit before and after with enough trials to separate the ranges.
