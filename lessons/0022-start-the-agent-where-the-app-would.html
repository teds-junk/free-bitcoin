This lesson answers: Inside the release tool, the agent does not start from a person's request: the tool first lists what was merged since the last release, then asks for the entries. How do I set that up for a stimulus?

The notes-cli team liked the skill enough to build it into their release tooling. Before each release, a small tool lists the pull requests merged since the last one and writes the list to a file. The tool then asks an agent, with the skill installed, to write the Unreleased entries for everything on the list. Nobody types a request, and nobody reads the entries before they ship. Every stimulus in part 1 was a person describing one change in their own words. This part asks whether the skill still holds when an app, not a person, starts the agent, and the first step is a stimulus that starts the agent exactly where the app does.

The stimulus is the app's situation

When you evaluate a feature of an app, the stimulus has two halves, and both come from the app. The prompt is whatever the app sends: usually short, always the same, and written by a developer rather than a user. The workspace is whatever the app has prepared by the time it calls the agent. A stimulus that rewrites the prompt in friendlier words, or hands the agent a tidier workspace, measures a situation the app never creates.

Copy the prompt from the app's code, word for word. For the workspace, run the app's own setup steps rather than writing their output by hand. If the team changes the list's format next month, an eval that runs their tool sees the new format; an eval with a hand-written copy of the old list keeps passing and tells you nothing.

Our release tool's prompt is one sentence: "Write the Unreleased changelog entries for every change listed in release/merged.txt." Its setup is one command that writes that file. The rest of this lesson reproduces both.

Source: Anthropic, Demystifying evals for AI agents (2026-01-09), on building tasks from the situations a deployed agent really meets.

Setting up before the agent starts

The release tool's first job is done by tools/list-merged.mjs, a short Node script. The real one asks the team's issue tracker. We have no tracker, so the copy the course ships prints a fixed list.

tools/list-merged.mjs
// Lists the changes merged since the last release, one per
// line, as "#<pull request> <type>: <summary>".
// The real release tool asks the team's tracker. This copy
// prints a fixed list, so every trial starts the same way.
const merged = [
  "#74 feat: add --since <date> to notes list",1
  "#75 fix: notes search missed titles with accents",
  "#76 refactor: move config loading out of cli.js",2
];

for (const line of merged) console.log(line);
  1. Each line starts with a pull request number and a type, as in the team's commit messages: feat is a new feature and fix a bug fix. Both change what users notice, so both need an entry.
  2. A refactor changes only the code. The skill says to add nothing for it. In part 1 the request said so too ("nothing changes for users"); here the list says only refactor, and the agent has to decide.

An eval file can run commands like this one. Inside an agent environment, commands: is a list of shell commands. Vally runs them in the workspace, in order, after it has copied the files and the skill and before the agent starts. Each command may take 60 seconds. A longer limit goes in commandTimeout, a key beside commands: in the same agent_environment, written as a length such as 2m. This lesson's eval file sets none.

That order matters for grading. A file made by a command is part of the starting state, exactly like a staged file: the agent can read it, and it does not appear in the patch. Only what the agent changes does. We checked this before writing the lesson, and our patches below show it.

evals/release.eval.yaml (the start)
name: release

defaults:
  timeout: 3m

agent_environment:
  skills:
    - ../skills/changelog-entry
  files:
    - src: fixtures/notes-cli/CHANGELOG.md
      dest: CHANGELOG.md
    - src: ../tools/list-merged.mjs1
      dest: tools/list-merged.mjs

stimuli:
  - name: since-last-release
    prompt: >-2
      Write the Unreleased changelog entries for every
      change listed in release/merged.txt.
    agent_environment:
      commands:3
        - "mkdir -p release"
        - "node tools/list-merged.mjs > release/merged.txt"
  1. The tool is staged into the workspace like the changelog. Its source is outside evals/, so the path starts with .., as the skill's does.
  2. >- joins the indented lines into one line of text, which is how the app sends its prompt. The | you used before keeps the line breaks; either would work here.
  3. The setup: make the release folder, then run the tool and save what it prints into release/merged.txt. The > sends a command's output to a file. Quote every command: a command containing a colon followed by a space is otherwise read as YAML structure, and the trial fails in milliseconds while vally lint says nothing.

Two more fields set up the start, and you will not need either here.

env: sets environment variables on the agent's process, one name and value per line. An app that passes settings to its agent that way would have them copied here. The values can appear in saved trials, so it is not a place for secrets.

git: builds the workspace from a git repository instead of copied files: type: worktree checks out a commit, tag or branch of a repository on your machine, and type: clone clones one from a URL. A real release tool would read the history this way. This course ships no repository, so we explain the field and do not run it. The shape, from the Vally docs:

From the Eval Spec reference (not run by us)
agent_environment:
  git:
    type: worktree
    ref: v2.1.0
    source: ../my-repo

A hidden test with run-command

What should the grader check? For every change on the list, the release needs the right number of entries: one line for each feature and fix, citing its pull request, and none for the refactor. That depends on the list, so the check has to read release/merged.txt, and a pattern on the diff cannot do that. It needs a script.

In lesson 6 you ran a script with the program grader, which reads a line of JSON that the script prints. The run-command grader is simpler. It runs a shell command in the graded copy of the workspace and passes when the command's exit code is 0. Exit code 0 means success, and anything else failure, as lesson 6 explained. A different expected code goes in expected_exit_code; stdout_contains and stdout_matches add checks on what the command prints; timeout defaults to 30 seconds. Because only the exit code matters, any existing test works unchanged: a test suite, a linter, a script like ours.

Stage the script through the grading environment and the agent never sees it. The Vally docs call these grader-only files, and a test run this way is a hidden test.

evals/grading/check-release.mjs
// Hidden test for the release stimulus. Each feature and
// fix in release/merged.txt needs a line of its own under
// Unreleased; a refactor needs none. Exit 1 means fail.
import { readFileSync } from "node:fs";

const merged = readFileSync("release/merged.txt", "utf8");1
const log = readFileSync("CHANGELOG.md", "utf8");
const start = log.indexOf("## [Unreleased]");
const end = log.indexOf("\n## [", start + 1);
const lines = log.slice(start, end).split("\n");2

for (const item of merged.trim().split("\n")) {
  const [, number, type] = item.match(/^#(\d+) (\w+):/);3
  const cite = "(#" + number + ")";
  const found = lines.filter((line) => line.includes(cite));
  if (type === "refactor") {
    if (found.length > 0) fail(cite + " is internal");4
  } else if (found.length !== 1) {
    fail(cite + " needs one line, found " + found.length);
  } else if (found[0].split("(#").length > 2) {
    fail(cite + " shares a line with another change");5
  }
}
console.log("every merged change handled");

function fail(why) {
  console.error(why);
  process.exit(1);6
}
  1. The list the setup command wrote. It is still in the graded copy, because it was part of the starting state.
  2. The lines of the Unreleased section: from its heading to the next version heading.
  3. From a line such as #74 feat: add …, take the number and the type.
  4. An entry citing the refactor fails.
  5. A feature or fix must be cited on exactly one line, and that line must not cite a second pull request. This catches a skipped change and two changes merged into one entry.
  6. Exit code 1 is the verdict. The reason goes to the error output, which helps when you run the script yourself; Vally's evidence records only the exit code.

The grader that runs it sits under the stimulus, beside a grading environment that copies the script in:

evals/release.eval.yaml (the end)
    grading_environment:
      files:
        - src: grading/check-release.mjs
          dest: .vally-grading/check-release.mjs
    graders:
      - type: run-command
        name: every-change-handled
        config:
          command: node .vally-grading/check-release.mjs

One limit to know before you rely on it: a hidden test needs the finished workspace, and Vally does not keep it. A later vally grade of these trials fails this grader on every trial, as it failed the program grader in lesson 8. Graders that read the patch or the trajectory can be re-graded; this one cannot.

Sources: Vally docs, Grader: run-command; Writing Eval Specs, Grader-only files.

What it showed

In our run no model skipped a change and none merged two into one entry. The failures were all one kind. The first model recorded the refactor in all five of its trials, filed under Changed in words that name a source file. The skill forbids both. The second model left the refactor out every time and said why in its reply.

In part 1 the refactor request told the agent that nothing changes for users. Here the list says only refactor, and deciding is left to the agent. That is the kind of difference an app introduces without anyone noticing: the same skill, a terser input, a rule that held before and now holds on one model only.

Passing the test is not the same as being right, either. Three of the second model's five entries for #74 said --since shows notes "created on or after a date", and the other two "only newer notes". The list says neither; it might as well filter by the date a note was changed. No grader we have checks for details the list does not support, and in an app nobody reads the entry before it ships.

One more thing in our report gives a clue to why the first model behaved as it did. The second model's table has a Skills column reading changelog-entry (5×); the first model's has no Skills column at all. The second model loaded the skill in every trial, the first in none. The hidden test sees only the finished changelog, so it cannot say whether the agent read the list, used the skill, or did anything else on the way.

Exercises

  1. From memory: a setup command creates a file, and the agent creates another. Which one can a diff grader see, and why?
    Show model answer

    Only the agent's. Setup commands run before the agent starts, so what they create is part of the starting state, like a staged file. The patch, which diff graders read, records only changes made after that.

  2. The team changes the tool to print the type first, as in feat #74: add --since …. What happens to the next run, and is that what you want?
    Show model answer

    The setup command runs the real tool, so release/merged.txt takes the new format at once. The hidden test's pattern ^#(\d+) (\w+): no longer matches, the script crashes, and every trial fails with exit code 1. That is the right signal: the eval noticed that the app changed. A hand-written copy of the old list would have kept passing. Update the test's pattern and run again.

  3. Why is run-command a better fit than a diff grader for this check?
    Show model answer

    What counts as correct depends on the list in release/merged.txt, which is not in the patch. A script in the graded workspace can read both the list and the changelog; a pattern on the diff sees only the changelog's changes.
