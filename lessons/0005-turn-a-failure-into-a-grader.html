This lesson answers: How do I make code decide whether a trial has one of these failures?

You could fix the skill now. Add a rule about pull request numbers, try it, look at the result, and feel better. But "look at the result" means reading patches again, on both models, several times each, after every edit, for as long as the skill lives. Nobody keeps that up. This lesson hands the reading to code: one small grader per failure mode, so that a single command tells you how often each failure happens, before your edit and after it.

What makes a grader worth having

Three habits separate graders that earn their keep from graders like the one in lesson 2.

Grade the result, not the route. An agent can reach a correct changelog by many routes: reading the file first or searching it, one edit or two. A grader that insists on a route fails every good route you did not think of. Look at what the agent left behind.

One grader per failure mode, named after it. When a grader called no-made-up-number fails, you know what went wrong without opening a file. A single grader that checks five things at once only tells you that something did.

A grader has to be able to fail. Lesson 2's grader passed almost anything. A grader that has never failed might be checking nothing. So the first time you run a new grader, run it where you already know the failure happens. If it passes there, the grader is wrong.

And use code for everything code can decide. A pattern costs nothing to run and gives the same answer every time. Some qualities on your list, such as whether an entry is written for users, are beyond a pattern. Those wait until lesson 12.

Sources: Vally docs, Choose a Grader, which says to prefer an exact check "when the requirement can be expressed exactly"; Anthropic, Demystifying evals for AI agents, 2026-01-09, on grading outcomes over paths.

Graders that read the diff

Three of the failure modes from lesson 4 are about what the agent added to the changelog, or whether it should have added anything. The patch already records exactly that. Vally has three graders that read it. They call it the diff, which is another word for the same thing.

GraderPasses when
diff-containsthe patch contains the text or pattern you give
diff-not-containsthe patch does not contain it
diff-emptythe agent changed nothing at all

One thing to know before using them: these graders see the whole patch, including the unchanged lines around the change. Here is the patch from a trial that made up a number.

workspace.patch (model: gpt-5.6-terra, before any edit)
4 lines hidden
@@ -7,6 +7,9 @@ All notable changes to notes-cli.
 ### Added
 - Add `notes list --tag` to filter by tag (#41)1

+### Fixed
+- Fix a typo in the `notes add` help text (#42)2
+
 ## [1.2.0] - 2026-09-14

 ### Added
  1. An unchanged line that happens to contain a pull request number. It is in the patch, so a grader that just looks for "a number in brackets" would find this one in every trial.
  2. The line that matters: one the agent added. A grader for made-up numbers has to look only at lines that begin with +.

These graders take either a value, which is exact text, or a pattern. A pattern is a regular expression: a short piece of text, written in a notation of its own, that describes the text to look for. You do not need to learn the notation. This course uses three patterns, and each is explained piece by piece.

Here is the first stimulus, complete, with the two graders you will add at its end.

evals/changelog.eval.yaml (the first stimulus)
  - name: typo-fix
    prompt: |
      I fixed the typo in the help text for `notes add`
      (it said "tittle"). Put that in the changelog.
    agent_environment:
      files:
        - src: fixtures/notes-cli/CHANGELOG.md
          dest: CHANGELOG.md
    graders:1
      - type: diff-contains2
        name: adds-an-entry
        config:
          value: "notes add"
      - type: diff-not-contains3
        name: no-made-up-number
        config:
          pattern: '(?m)^\+.*\(#\d+\)'4
  1. graders goes last in the stimulus, lined up under agent_environment.
  2. Did the agent add an entry at all? The starting changelog never mentions notes add, so that text can only be in the patch if the agent wrote it.
  3. Passes only if the pattern is found nowhere in the patch.
  4. The pattern, in single quotes so that its backslashes are kept exactly as typed. In words: an added line that contains a hash and digits in brackets.

Read the pattern from left to right.

PieceMeaning
^The start of a line.
(?m)A switch, written at the front. It makes ^ mean the start of every line. Without it, ^ means only the very start of the whole patch.
\+A plus sign. So ^\+ is a line that starts with a plus: a line the agent added.
.Any one character.
*The piece before it, repeated any number of times. So .* is "anything", up to the end of the line.
\(#An opening bracket and a hash.
\d+One or more digits.
\)A closing bracket.

The backslashes are there because +, ( and ) have special meanings in a pattern, and a backslash says "this character itself".

  1. The refactor changes nothing for users, so the right result is no change to the changelog. diff-empty takes no config.
  2. An added line that starts with ### Security: the agent created a Security category.

When a stimulus has more than one grader, a trial passes only if every grader passes. vally lint prints a warning named scoring-defaults-applied to tell you that this rule is in force. It is the rule you want, so the warning is expected.

Why does the pattern for no-made-up-number ask for a line that starts with a plus sign?
Right. The patch also contains unchanged lines, and one of them ends with (#41). Requiring a leading plus sign limits the grader to what the agent wrote.
So that only added lines can match. The patch includes unchanged lines around the change, and one of them ends with (#41). Without the plus sign the grader would object to every trial.
Sources: Vally docs, Grader: diff-contains; Grader: diff-empty; Scoring. That these graders see unchanged lines is from our test on 2026-11-10 with Vally 0.21.0.

Measure, edit the skill, measure again

You will add the graders above to an eval file, run it against the skill as it is, add three rules to the skill, and run again. These are the rules, one per failure mode. Each names a case the skill left open and says what to do. The first also says not to stop and ask: when a skill is used unattended, as it is in every Vally run, nobody is there to answer, so we chose "leave it off". You will add them to the end of the skill in step 5.

skills/changelog-entry/SKILL.md (lines to add at the end)
- If no pull request number is given, leave the reference
  off. Never make one up, and do not stop to ask.
- If a change makes no difference to people who use the
  tool, such as a refactor, add nothing and say so.
- The categories, in this order: Added, Changed, Deprecated,
  Removed, Fixed, Security. A security fix goes under
  Security.

What the counts show

That last row is the reason for this whole course. One edit, three rules, and on one model all three took. On the other, the same words fixed one failure and left another only partly fixed. Reading a couple of patches by hand might well have shown you the model where it worked. The count shows you both, and it will show you again, in three minutes, after your next edit.

Notice also what the graders did in step 3. Every one of them failed somewhere, on trials you already knew were bad from your own reading. That is a first piece of evidence that they check what you meant. Lesson 7 makes that test deliberate.

Choose a Grader, Vally docs

Read "Choose by evidence": it sorts Vally's graders by what each one looks at, which is the fastest way to find the right one for a failure mode.
