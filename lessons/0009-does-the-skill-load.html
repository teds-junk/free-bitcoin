So far: You have graders you have tested, and a skill whose rules you have improved twice. In every trial so far, the skill was the only one installed and every request said "changelog".

This lesson answers: Does the agent load the skill for the requests it is meant for, and leave it alone for the others?

All the rules you have added to the skill do nothing unless the agent reads them. And an agent does not read every skill it has. It reads a one-line description of each, and opens a skill only when that line seems to fit the request. Your skill's description is still the one from the first draft: "Adds an entry to the project changelog." So far that has been tested only in the easiest possible conditions. This lesson tests it in harder ones, and then improves it.

The description decides

When an agent starts, it is given the name and description of every installed skill, and nothing else about them. When a request arrives, the model decides whether any description fits. If one does, the agent loads that skill, which means it reads the rest of SKILL.md. If none does, the instructions are never seen.

That gives two new ways for a skill to fail, both invisible to the graders you have written.

  • It does not load when it should. The agent does the task anyway, from its own habits, without your rules. The result may even look fine.
  • It loads when it should not. The agent applies changelog rules to a task that is not a changelog entry.

The first is common. In one vendor's 2026 report, a skill went unused in 56% of the cases it was meant for. That figure is the vendor's own, and the number of runs behind it was not published, but the pattern is widely reported.

Obvious requests test neither failure well. "Update the changelog" will load a changelog skill almost whatever its description says. The informative requests sit near the edge.

Near-miss request

A request that shares words or a subject with the skill's job, but is not its job. "Draft the release notes from the changelog" mentions the changelog and is not a request for a changelog entry.

A loading test therefore needs two groups: requests that should load the skill, including ones that never use its obvious word, and near-miss requests that should not. And it needs to observe what the agent did. Asking a model "would you use this skill?" tests what it says, not what it does.

When a test shows the description is at fault, a better one says three things: what the skill does, when to use it, described as a situation and not as a word to look for, and what it is not for.

How big should such a test be? For a skill you depend on, the guidance in this lesson's primary source is about twenty requests and three trials each, with some requests kept aside that you never look at while rewording, so that you are not just fitting the description to your test. Those numbers are conventions; nobody has published a calculation behind them. This lesson uses six requests and two trials, which is enough to learn the method.

Sources: agentskills.io, Optimizing skill descriptions, which uses "near-miss" for these requests; Vercel, AGENTS.md outperforms skills in our agent evals (vendor-reported, run counts not disclosed).

How a trial records loading

When an agent loads a skill, Vally records an event in the trial's trajectory. It is named skill_activation. Vally's words for this one thing vary: the event says "activation", the grader below is named skill-invocation, and its evidence says a skill was or was not "called". All three mean what this course calls loading. Spread out, one event looks like this:

results.jsonl (one event inside one trial's trajectory)
{
  "type": "skill_activation",1
  "timestamp": "2026-11-10T14:55:54.427Z",
  "data": {
    "name": "changelog-entry",2
5 fields hidden: path, full text, 3 empty
  },
  "turn": 03
}
  1. The kind of event. One is recorded each time a skill is loaded.
  2. Which skill was loaded.
  3. Which turn of the conversation it happened in, counting from 0. Every trial so far has had one turn; lesson 11 has more.

You rarely need to open that. The report has a column named Skills, which lists the skills that loaded in each stimulus's trials and how many times. A dash means none loaded.

  2. A request that should load the skill and never says "changelog".
  3. Passes only if changelog-entry loaded.
  4. A near-miss request: it mentions the changelog and belongs to a neighbour.

The four stimuli hidden above follow the same two shapes. load-plain says "Update the changelog". load-indirect asks that users be able to see a fix when the tool ships. skip-commit asks for a commit message. skip-question asks what changed in a past version.

These graders have no name, so Vally names them itself, for example skill-invocation requires changelog-ent…. Loading varies from trial to trial like everything else, so the checkpoint runs each stimulus twice.

A skill's description may run over several lines if it begins with >-, as the new one in the checkpoint does.

If you ever read a trial's record, you will see that the agent is offered a few skills besides yours. They come with Copilot itself; on our machine there were three. They are not part of this course, and the graders ignore them.

Test loading, then fix the description

You will run the loading eval as the skill stands, read the Skills column, rewrite the description, and run again. This is the new description, for step 6. It replaces the one description line at the top of the skill.

skills/changelog-entry/SKILL.md (the new description)
description: >-
  Records a change in the project's CHANGELOG.md. Use whenever
  a change, fix or merged pull request should be noted for the
  next release, even if the request does not say "changelog".
  Not for commit messages, release notes or questions about
  past versions.

What the loading test showed

Our result is undramatic, and that is worth being honest about. With only two neighbours, the one-line description already kept the skill out of every near-miss. It missed once: on one model, the request that never says "changelog" was handled without loading the skill. The agent edited the changelog anyway, from habit, with none of your rules in front of it. After the rewrite, the skill loaded in every finished trial that should load it.

One miss in two trials becoming none in two is a small sample, and lesson 15 will make you cautious about it. What you have for certain is the test itself. Real projects install dozens of skills, descriptions get edited, and neighbours get added. Each of those can move the boundary, and now one command shows whether it did.
