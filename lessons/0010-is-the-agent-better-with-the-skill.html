So far: Your skill loads when it should, and with it loaded both models pass most of your graders.

This lesson answers: Are the results better with the skill than without it?

In lesson 9 one trial did the job without loading the skill, and the result looked plausible. That raises an awkward question. Models already know what a changelog is. Perhaps they would pass your graders with no skill at all, and the skill is decoration. Or perhaps the skill matters a great deal. You have measured the skill against earlier versions of itself, and never against nothing. This lesson does that, and turns up something about the first draft that none of the earlier lessons could have shown.

A skill has to beat no skill

A skill costs something. It adds to the text the model has to read on every request, it has to be maintained, and it can be wrong. It earns its place only on requests where the agent does better with it than without.

You cannot assume it does. One 2026 study ran the same 87 tasks with and without skills. Skills written with care raised the share of tasks completed by about 17 percentage points on average, yet made 13 of the 87 tasks worse. Skills that the models wrote for themselves lowered it.

The way to find out is a fair comparison: the same stimuli, the same graders, the same model, and one difference, whether the skill is installed. Lesson 7 defined a baseline as what you compare a result against. Here the baseline is the run with no skill.

Expect three kinds of answer, stimulus by stimulus. The skill helps: it fails without and passes with. The skill makes no difference: the model manages either way, and the skill is not earning anything there. The skill hurts: it passes without and fails with. All three are worth knowing.

Source: SkillsBench, version 4, 2026 (a preprint; one benchmark of 87 tasks).

An experiment file

Variant

One version of the set-up being compared: the same eval, run with one setting changed. "With the skill" and "without the skill" are two variants.

An experiment file lists variants of an eval, and one command runs them all. The starter folder has one.

evals/with-and-without.experiment.yaml
name: with-and-without

evals:
  - changelog.eval.yaml1

vary: [/environment/skills, /defaults/model]2

baseline: haiku-no-skill3

variants:
  haiku-no-skill:4
    overrides:
      model: claude-haiku-4.55
    environment:
      skills: []6
  haiku-with-skill:
    overrides:
      model: claude-haiku-4.5
    environment:
      skills: [../skills/changelog-entry]7
10 lines hidden: the same two variants for gpt-5.6-terra
  1. The eval file to run, relative to this file. Its stimuli and graders are used unchanged in every variant.
  2. The settings the variants are allowed to differ in. Each is written as a path into the eval's settings: /environment/skills is the list of skills in the agent environment, and /defaults/model is the model. If a variant differs in anything else, Vally refuses to run and reports Experiment drift detected. That is what keeps the comparison fair.
  3. The variant the others are compared with.
  4. A variant's name. You choose it.
  5. The model for this variant. overrides replaces settings from the eval file's defaults, and model here is the /defaults/model named under vary. An experiment sets the model in the file, and not on the command line.
  6. An empty list: no skill installed.
  7. The skill installed, as in the eval file. An experiment file says environment where an eval file says agent_environment; they mean the same.

The command is vally experiment run, followed by the experiment file. It accepts --workers and --output-dir as vally eval does. Adding --dry-run makes it print the plan, one block per variant, without starting an agent, which is the experiment's version of lint.

When it finishes it prints a table with one column per variant, counting the stimuli that passed, and beneath it each variant's total tokens over all its trials and its trial time. The run folder has one subfolder per variant, named after it, each with its own results.jsonl and a folder for the eval laid out like the ones you already know. The report is one file for the whole experiment, report.md, in the run folder itself. An experiment writes it instead of a single eval's eval-results.md, with a heading and a table for each variant.

In an experiment, one variant uses a different model, and the model is not listed under vary. What happens?
Right. Variants may differ only in the settings listed under vary. Anything else is reported as drift, so a result cannot quietly depend on a second difference.
Vally refuses and reports experiment drift. Variants may differ only in the settings listed under vary, so that a result cannot quietly depend on a second difference.
Sources: Vally docs, Run Your First Experiment; Experiment File Schema. The drift message is from our test on 2026-11-10 with Vally 0.21.0.

What the comparison showed

In our run the answer to this lesson's question is yes: five of five with the skill on both models, three of five on each without. The skill is earning its place on the refactor and the security fix. Both models handled the missing Unreleased section on their own.

Now look at the patch in step 5. With no skill installed, the model that kept inventing (#42) in lessons 1 to 5 did not invent anything. Neither model did. The made-up pull request number was not a weakness of that model that your skill failed to prevent. Your first draft caused it. "Reference the pull request", with no word on what to do when there is none, pushed a model into making one up.

That is the third kind of answer from the section above: a skill making a result worse. You fixed it in lesson 5 without knowing its cause. Only a comparison with no skill could show it, which is a good reason to run one before trusting any skill, and again after any large edit.

The skill did not cost tokens either. It adds text for the model to read, yet in our run both models used fewer tokens with it than without: 360.0k against 371.0k on claude-haiku-4.5, and 255.0k against 280.9k on gpt-5.6-terra, over five trials each. That is too few trials to say the skill saves tokens; it is enough to see that it does not cost many. Lesson 16 turns tokens into money.

Each cell of the table is one trial per stimulus, so treat small differences with care. A stimulus that fails without the skill in every model is solid evidence. A single cell that differs is a reason to run more trials.

Exercises

  1. From memory, name the three kinds of answer a with-and-without comparison can give for a stimulus.
    Show model answer

    The skill helps: the stimulus fails without it and passes with it. The skill makes no difference: it passes, or fails, either way. The skill hurts: it passes without the skill and fails with it.

  2. Two stimuli pass without the skill on both models. Does that mean they should be removed from the eval file? Give a reason.
    Show model answer

    No. They show that the skill adds nothing there today, but they also guard against the skill making those requests worse after a future edit, which is exactly what the first draft did to the typo fix. Keep them as checks that what works keeps working.
