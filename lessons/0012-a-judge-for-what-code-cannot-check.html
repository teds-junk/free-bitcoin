So far: Every grader you have written is code: a pattern, an empty-diff check, a script, or a check of which skills loaded. Each checks something code can see.

This lesson answers: How do I grade a quality that no pattern can decide?

Since lesson 1 the skill has said entries should be "written for people who use the tool". In lesson 4 you saw a model ignore that: asked to record a fix that swapped in a streaming parser, it wrote an entry about the streaming parser. No grader has checked this since, because none can. "Mentions an implementation detail" is not a pattern. A user cares that big imports no longer crash; the words that give away the coding could be anything. Checking it takes something that can read. That something is another model, and this lesson shows how to use one without fooling yourself.

When a judge is the right tool

LLM judge

A grader that asks a language model to read what the agent did and decide whether it meets a criterion you wrote. LLM stands for large language model.

A judge can decide things code cannot. It is also slower than code, it costs a model call for every trial, and it can be wrong in ways a pattern never is: it may be swayed by confident wording, or read your criterion differently from you. So the first rule is to use one only for what code cannot decide. Everything you graded in lessons 5 to 11 should stay with code.

When you do need one, three habits make its verdicts usable.

One question per judge. A judge asked whether an entry is "good" has to weigh several things at once, and you cannot tell which one tipped it. Ask about one quality.

Yes or no. A score from 1 to 5 feels more informative and is harder to act on. Nobody, including the judge, can say what separates a 3 from a 4. A yes-or-no answer forces the criterion to be clear.

Decide your own answers first. Before writing the criterion, read real examples and say yes or no to each yourself. If you hesitate, your criterion is not yet clear, and the judge will inherit the muddle. Each answer you write down is called a label, and your labels are what you will check the judge against in lesson 13.

Source: Hamel Husain, Using LLM-as-a-Judge, on binary judgements and on writing your own verdicts before the judge's.

How Vally's judge decides

Vally's judge is a grader of type prompt. The name is unlucky: it has nothing to do with the prompt: that holds a stimulus's request. It needs three things, in three places in the eval file.

evals/wording.eval.yaml (with a judge added)
defaults:
  timeout: 3m
  judge_model: claude-sonnet-5.51
9 lines hidden: the agent environment
  - name: parser
5 lines hidden: the request
    rubric:2
      - The new changelog entry says what changes for people
        who use the tool, and does not say how it was coded.
    graders:
      - type: prompt3
        config:
          scoring: binary4
          prompt: Begin your reason by quoting the new entry.
      - type: diff-contains
3 lines hidden: the grader for the pull request number
  1. The model that does the judging. Name it: if you leave it out, Vally picks one, and its choice can change from one version of Vally to the next. Choose a model that is not one of the two you are testing, so that no model marks its own work.
  2. The rubric: a list of criteria for this stimulus, in plain words. This one has a single criterion.
  3. The judge. It reads the rubric of the stimulus it sits in.
  4. scoring: binary makes the answer yes or no. The line below it is an extra instruction to the judge; this one makes each reason start with the entry, so you can see what the judge was looking at.

When the judge runs, Vally gives the judge model the request, the rubric, and files holding what the agent said and did in that trial. The judge reads them and returns a verdict and a reason. The verdict becomes the grader's pass or fail, and the reason becomes its evidence.

The judge returns one overall verdict for the stimulus. With one criterion in the rubric, that verdict is the answer to your one question. With several criteria it would be a blend, which is the second reason to keep to one.

Here are two of the judge's reasons from our run, as they appear in the output.

VerdictThe judge's reason
✗The new entry is "Fix out-of-memory errors when importing large files by using a streaming parser in importer.js (#49)". It gives the user-facing fix but also describes the implementation (streaming parser, importer.js), which violates the criterion.
✓The new entry is "Parse dates with single-digit months and days (#67)". It sits under Fixed in Unreleased, is user-focused, and has no implementation details.

Because a judge is a grader, vally grade can run it over trials you have already saved. You can reword the rubric and judge the same trials again without paying for the agents twice. Each judged trial is one request to the judge model, charged to your Copilot plan as an agent run is. With vally grade, as with the oracle, --verbose prints every grader's evidence, which for a judge is its reason.

Why does this lesson's rubric have one criterion and not three?
Right. The judge gives one overall verdict. With one criterion, a "no" tells you exactly what was wrong.
One verdict then answers exactly one question. A rubric may list several criteria, but the judge returns one overall verdict, and with several criteria you could not tell which one caused a "no".
Sources: Vally docs, Grader: prompt; Eval Spec reference. The two reasons are from our run on 2026-11-10 with Vally 0.21.0.

What the judge found

You now have a grader for the oldest unchecked line in your skill, and it has already told you something. In our run four of the six "no" answers came from one model, which named the parser or the cache every time. The other named its method only in the cache entry. "Written for people who use the tool" is followed unevenly, and until now nothing could show that.

Resist acting on it just yet. Every grader before this one was code that you tested with the oracle and against saved trials. This one is a model's opinion. Its reasons read well, and a well-written reason is not evidence of a correct verdict.
