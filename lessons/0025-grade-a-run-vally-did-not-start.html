This lesson answers: The app ran the agent itself, from a few shell commands, and recorded what it did as traces. Can Vally grade that run?

Everything so far has happened inside Vally: Vally prepared the workspace, started the agent, recorded the trajectory and graded it. The notes-cli team's release tool does not work that way. After a merge, a script prepares a checkout, and a small program, the release app, opens an agent session and sends its request. Nobody runs Vally. What the team has afterwards is the changed checkout and the app's own record of the session. If your graders can read that record, every real run of the app can be checked with the same eval file you have been building since lesson 22.

Inside Vally or after the fact

There are two ways to put an app's agent under your graders, and they answer different questions.

  • After the fact. The app runs as it always does, and you grade what it recorded. You see the real thing: the app's own settings, its real inputs, its real model. But each run happens once. You cannot ask for five more trials of the same situation, or the same situation on another model.
  • Inside Vally. Vally starts the agent, so it can repeat a stimulus, vary the model and run experiments. But what it runs is a reproduction of the app, and a reproduction can differ from the app in ways that matter.

Most teams want both: trials inside Vally to decide whether a change is safe, and grading of real runs afterwards to see whether what was decided still holds. This lesson does the second. Lesson 26 does the first with the app's own code.

A trajectory from outside

vally grade has always read trajectories. In lesson 8 they came from Vally's own results.jsonl. It also reads a second, public format, which any program can write.

ATIF

The Agent Trajectory Interchange Format: a JSON file describing one agent session as a list of steps. Each agent step holds what the model said, the tool calls it made, an observation holding what each call returned, and metrics such as tokens. Vally converts an ATIF file into its own trajectory before grading.

One more flag, --stimulus, names the stimulus whose graders apply, because an ATIF file does not say which stimulus it answers. Hidden test files under grading_environment are staged for the graders as they are in a normal run, so the hidden test from lesson 22 works too.

The graders see only what the file records. Three gaps matter here. Vally's cost stays empty for ATIF input: it understands only the Copilot runtime's own AIU, so the cost_usd in each step is kept in the file but not added up. The trial's wall time is recorded as 0, because the file has no start and end time for the session. And a skill counts as loaded only if the trajectory shows the agent calling its skill tool.

From OpenTelemetry traces

The release app does not write ATIF. Like most programs built on an agent library, it writes traces.

OpenTelemetry

An open standard and toolkit for recording what a program does as it runs, so that any tool can read the record. Its records of work done are traces.

Span

One unit of work inside a trace, such as one call to a model or one tool call, with a start time, an end time and attributes: named values describing the work. Every span carries the ID of its trace and its own ID; a span started inside another records that one as its parent. A span with no parent is the root of its trace.

GenAI semantic conventions

OpenTelemetry's agreed names for spans and attributes that describe AI work: a chat span for a model call, an execute_tool span for a tool call, an invoke_agent span for a whole agent session, and attributes such as gen_ai.usage.input_tokens. Because the names are shared, a converter written for one library's traces mostly works for another's. The conventions are still marked "Development", so names can change.

Sources: OpenTelemetry, Traces ("A span represents a unit of work or operation"); OpenTelemetry, Semantic conventions for GenAI spans, Status: Development (the page at opentelemetry.io now points there). Both read 2026-11-10.

The release app is shipped in app/. It is built on the GitHub Copilot SDK, the same library Vally's own executor uses to run an agent. The SDK takes a telemetry setting and writes every span as one line of JSON to a file. This is the app's command-line entry point, all of it:

app/run.mjs
// Run the release assistant once, with tracing to a file:
//   node app/run.mjs <repo> <skills> <model> <traces file>
import path from "node:path";
import { writeEntries } from "./release-assistant.mjs";1

const [repo, skills, model, traces] = process.argv.slice(2);
const { reply } = await writeEntries({
  repoDir: path.resolve(repo),
  skillDirs: [path.resolve(skills)],
  model,
  timeoutMs: 180000,
  telemetry: {2
    exporterType: "file",
    filePath: path.resolve(traces),
    captureContent: true,3
  },
});
console.log(reply);
  1. The app itself, app/release-assistant.mjs: forty lines that start an agent session in the checkout, with the team's skill, send the request "Write the Unreleased changelog entries for every change listed in release/merged.txt." and wait for the reply. The same request as the stimulus in your eval file.
  2. Write spans to a file, as JSON lines.
  3. Include message text, tool arguments and tool results in the spans. Without it the spans hold names and counts only, and no grader could check what a tool call did.

Vally writes spans of its own (the otel-spans.jsonl file in every run folder), but it does not read traces in. So the starter ships a converter, app/traces-to-atif.mjs, about seventy lines. It sorts the spans by start time, then walks through them:

app/traces-to-atif.mjs
31 lines hidden: read and sort the spans
for (const span of spans) {
  const a = span.attributes;
  session = a["gen_ai.conversation.id"] ?? session;
  if (a["gen_ai.operation.name"] === "chat") {1
    model = a["gen_ai.request.model"];
    steps.push({
      step_id: steps.length + 1,
      source: "agent",
      model_name: model,
      message: textOf(a["gen_ai.output.messages"]),
      tool_calls: [],
      observation: { results: [] },
      metrics: {2
        prompt_tokens: a["gen_ai.usage.input_tokens"],
        completion_tokens: a["gen_ai.usage.output_tokens"],
        cached_tokens:
          a["gen_ai.usage.cache_read.input_tokens"],
        // A billion nano-AIU is one AI Credit: $0.01.
        cost_usd: (a["github.copilot.nano_aiu"] ?? 0) / 1e11,
      },
    });
  } else if (a["gen_ai.operation.name"] === "execute_tool"
      && steps.length > 0) {3
    const step = steps[steps.length - 1];
    const id = a["gen_ai.tool.call.id"];
    step.tool_calls.push({
      tool_call_id: id,
      function_name: a["gen_ai.tool.name"],4
      arguments: argumentsOf(a["gen_ai.tool.call.arguments"]),
    });
    step.observation.results.push({
      source_call_id: id,
      content: a["gen_ai.tool.call.result"] ?? "",
    });
  }
}
8 lines hidden: print the ATIF file
  1. Each model call becomes a new step. Every other span (the session's setup, permission checks, timings) is skipped.
  2. The span's token attributes, renamed to ATIF's names.
  3. A tool call belongs to the model call just before it, because the model asked for it there.
  4. The tool name, and on the next line its arguments. argumentsOf parses them as JSON. One tool, apply_patch, which gpt-5.6-terra uses to edit files, records its arguments as plain text, so the helper keeps that text under input. Our first version did not, and failed on terra's trace.
Trace files hold private values

A trace written with content captured holds the whole prompt, every file the agent read, full paths on your machine, and an attribute enduser.pseudo.id that identifies your account. Do not attach raw traces to an issue or commit them. Everything on this page was cleaned first.

The script the release tooling runs

The last piece is the script the release tooling runs, app/run.sh. It does by hand what your eval file's agent_environment and commands: do inside Vally, then runs the app and records the change. It uses no git, so the change is a plain diff between a copy of the folder from before and the folder after.

app/run.sh
9 lines hidden: usage notes, as in the text
set -e1
rm -rf app-run
mkdir -p app-run/repo/release app-run/repo/tools
mkdir -p app-run/skills

# The checkout: the same files the eval file stages.
cp evals/fixtures/notes-cli/CHANGELOG.md app-run/repo/2
cp tools/list-merged.mjs app-run/repo/tools/
cp -R skills/changelog-entry app-run/skills/

# The release tooling's own setup step.
cd app-run/repo
node tools/list-merged.mjs > release/merged.txt3
cd ../..
cp -R app-run/repo app-run/before4

# The app itself: one agent session, traced to a file.
node app/run.mjs app-run/repo app-run/skills "$1" \5
  app-run/traces.jsonl

# What changed. diff exits 1 when it finds a difference.
cd app-run
diff -ruN before repo > change.diff || true6
echo "Wrote app-run/traces.jsonl and app-run/change.diff"
  1. Stop at the first command that fails. Each run first deletes the previous app-run/.
  2. The checkout gets the fixture changelog and the tool, as your eval file stages them; the skill goes in a folder of its own beside it.
  3. The same setup command as your eval file's commands: step.
  4. A copy of the starting state, taken after setup. Like Vally's baseline, it makes release/merged.txt part of the start, not of the change.
  5. "$1" is the model you give the script.
  6. Compare the two folders. -r goes into subfolders, -u writes the usual diff format, and -N shows new files as added.

What carried over

Every grader you wrote inside Vally worked on a run Vally never saw. The hidden test ran in a copy of the app's checkout and caught the refactor's entry. The tool-calls graders found the view of merged.txt and no git commit, because the traces recorded every tool call with its arguments. max-repeat counted repeated calls from the same record, and skill-invocation saw that no skill call was made. Those graders answer "did this run do the job, the way the app needs?", and that question has the same answer however the run was started.

Some things did not carry over, and each one traces back to what the file records. cost was empty, so a cost comparison has to add up cost_usd itself. The wall time was 0, so a wall-time grader would pass anything. Skill loading counted only because the agent's skill call is an ordinary tool call in the trace; an app that loaded skills some other way would show none. Before trusting a grader on converted runs, ask whether the field it reads came across. And the tracker-down stimulus has nothing to grade here: its tool fails only because Vally makes it fail, and the app's real runs never had that bad day on purpose.

The comparison raised a question the graders cannot answer. On haiku, the app's run failed the way Vally's own trials mostly did. Is the app as good as Vally's runs, worse, or better? With one run of the app there is no way to say, and that is the limit of grading afterwards: each real run happens once, on whatever model the app used.
