So far: You have written a skill for an AI agent, or are about to, and you have tried it by hand.

This lesson answers: My skill works when I try it. Does it do the same thing on another model?

You write a skill, try it once, and the agent does what you wanted. Then a teammate uses it with a different model and gets something else, and neither of you can say which result is normal. This course is about replacing "it worked when I tried it" with evidence. It follows one small skill from a first draft to a version you can defend, and this lesson starts by showing the problem on your own machine.

A skill is advice, and each model reads it its own way

Skill

A folder containing a file named SKILL.md: a name, a one-line description, and instructions. An AI agent loads the instructions when a task matches the description.

An agent is a program that uses a language model to carry out a task with tools: it reads files, edits them and runs commands. The model is the part that decides what to do. The same agent can run on different models.

The skill this course improves is about one small chore: keeping a changelog.

Changelog

A file, usually named CHANGELOG.md, that lists what changed in each version of a tool, for the people who use it. Changes that have not shipped yet go under a heading called Unreleased, grouped into categories such as Added and Fixed. Each line is one entry. An entry often ends with a reference such as (#41), the number of the pull request that made the change. A pull request, or PR, is a numbered proposal to change a project's code.

Here is the skill. It tells an agent how to add an entry, and it is a plain first draft, the kind written in five minutes.

skills/changelog-entry/SKILL.md
---
name: changelog-entry
description: Adds an entry to the project changelog.
---

# Changelog entry

Use this when a change needs to be recorded in CHANGELOG.md.

- Add the entry under Unreleased, in the right category.
- One line per change, written for people who use the tool.
- Reference the pull request.
- Leave released versions alone.

Read it the way a model has to. "The right category": which categories exist? "Reference the pull request": in what form, and what if there is no pull request? The skill does not say, so each model fills the gap with its own guess. When you try the skill by hand you see one model's guess, once. That is one observation, and it tells you little about the next model or the next request.

Source: agentskills.io, the open description of the skill format.

What one Vally run does

Vally is a command-line tool that runs an agent for you in a controlled way and keeps a record of what it did. The agent it runs is the one that comes with GitHub Copilot, which is why this course needs a Copilot account.

Eval

A repeatable test of an agent: the same request, in the same starting folder, checked the same way every time.

An eval is described in an eval file. The starter folder for this course has one, evals/one-request.eval.yaml. It holds a single request ("I fixed the typo in the help text for notes add (it said "tittle"). Put that in the changelog."), the starting files, and one check. Lesson 2 reads that file line by line. For now, this is what happens when you run it:

  1. Vally makes a fresh scratch folder and copies in the starting files and the skill.
  2. It starts an agent on the model you named and gives it the request.
  3. When the agent stops, Vally saves a record of what the agent changed.
  4. It runs the check and prints a tick or a cross.
Workspace

The scratch folder an agent works in during one run. Vally creates a new one for every run, so no run can see what another did.

The command is vally eval. It takes three things in this lesson:

  • -e, followed by the path of the eval file to run.
  • --model, followed by one model name, or several separated by commas. With several, Vally does the whole run once per model.
  • --output-dir, followed by the folder to save results in.

It writes only inside that results folder. It does spend requests from your GitHub Copilot plan: each run is one short session, meaning one conversation with the agent.

Long commands in this course are split over several lines, with a backslash at the end of every line but the last. Type them as shown, or on one line without the backslashes.

If the agent's connection drops, the run does not finish and Vally prints ERROR for that model. That says nothing about the skill. Run the command again.

Model names differ from account to account. If you name a model your account does not have, Vally stops before starting any agent and prints the names you do have. The checkpoint uses that to show your list. The command still needs --output-dir, and Vally writes a small record of the failed attempt there.

Sources: Vally docs, How It Works; Vally docs, CLI: eval. The behaviour with an unknown model name is from our run on 2026-11-10 with Vally 0.21.0.

Reading a patch

Patch

A text file that records a change to other files as lines added and lines removed.

Step 3 above, "saves a record of what the agent changed", produces a patch. Vally writes one for every run and names it workspace.patch. It saves the results of each command in a folder named with the time the command started. Inside that folder, the patch is under the eval's name, then the request's name, then the model, then a run number that starts at 0. This is a real patch, from the run you are about to repeat:

workspace.patch (model: claude-haiku-4.5)
diff --git a/CHANGELOG.md b/CHANGELOG.md1
index 616c9f6..5045ff4 100644
--- a/CHANGELOG.md
+++ b/CHANGELOG.md
@@ -7,6 +7,9 @@ All notable changes to notes-cli.2
 ### Added3
 - Add `notes list --tag` to filter by tag (#41)

+### Fixed4
+- Fix typo in help text for `notes add` command
+
 ## [1.2.0] - 2026-09-14

 ### Added
  1. The file that changed. The next three lines repeat it in other forms; you can skip them.
  2. Where in the file the change is: starting at line 7.
  3. A line that begins with a space was already there and is unchanged. These lines are context, so you can see where the change sits.
  4. A line that begins with + was added by the agent. A line that begins with - would be one the agent removed; this patch has none.

So this model added a "Fixed" heading and one entry under "Unreleased", and touched nothing else. You can read exactly what an agent did to a file without opening the file.

In a patch, a line begins with a single space. What does that tell you?
Right. A leading space marks context: a line that was already in the file and still is.
The line was there and unchanged. Added lines begin with a plus sign and removed lines with a minus sign; a leading space marks unchanged context around the change.

Run it on two models

You will copy the starter folder, look at the skill and the changelog, find your account's model names, run the one request on two models, and read the two patches.

Both models get the same skill, the same changelog and the same request. The request does not mention a pull request. What do you expect each model to do about "Reference the pull request"?

Check your prediction

Do the checkpoint first and look at your own two patches. In our run, one model left the reference off and the other made up a pull request number.

One request, two models

  1. Goal: confirm the tools are installed. 
    node --version
vally --version

    You should see: a Node version of 22.15 or higher, then 0.21.0. If either command is missing, follow Before you start on the course home.

  2. Goal: make your own practice folder from the starter. This creates a new folder named practice. Open a terminal in the course folder: the one this course came in, which contains index.html and practice-starter. 
    cp -R practice-starter practice
cd practice

    You should see: nothing printed. Every lesson's checkpoint starts in practice.

  3. Goal: read the skill you will be improving. 
    cat skills/changelog-entry/SKILL.md

    You should see: the thirteen lines shown at the top of this lesson.

  4. Goal: read the changelog the agent will be asked to edit. It is in evals/fixtures, the folder for starting files. 
    cat evals/fixtures/notes-cli/CHANGELOG.md

    You should see: a changelog for a made-up tool, notes-cli. Find the "Unreleased" section. It has one entry, which ends with (#41), a reference to pull request 41.

  5. Goal: see the model names your account has. This starts no agent and spends nothing. 
    vally eval -e evals/one-request.eval.yaml \
  --model list-my-models \
  --output-dir results/models

    You should see: the word ERROR, then Model "list-my-models" is not available in Copilot. Available models: followed by a list. Yours will differ from ours. Pick two. This course used claude-haiku-4.5 and gpt-5.6-terra, checked on 2026-11-10.

  6. Goal: run the request on both models. This spends two short agent runs from your Copilot plan. Put your two model names in place of the course's. 
    vally eval -e evals/one-request.eval.yaml \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --output-dir results/lesson-1
    Model summary
  ✓ claude-haiku-4.5  1/1 evals passed
  ✓ gpt-5.6-terra     1/1 evals passed

  eval         claude-haiku-4.5  gpt-5.6-terra
  one-request  ✓ 1/1             ✓ 1/1

    You should see: a tick for each model, after about twenty seconds, then a line beginning Saved that names the results folder. "1/1 evals passed" counts eval files, and you ran one. If a model shows ERROR, the run did not finish, usually a dropped connection: run the command again.

  7. Goal: find the folder this run was saved in. 
    ls results/lesson-1

    You should see: one folder named with the time of your run, such as 2026-11-10T14-55-22-404Z. Use your folder's name in place of that one in the next step.

  8. Goal: move into the saved results for this request, so the next paths are short. 
    cd results/lesson-1/2026-11-10T14-55-22-404Z
cd one-request/typo-fix
ls

    You should see: one folder for each model you named. The two folders you moved through are named after the eval and the request; lesson 2 explains where those names come from.

  9. Goal: read what the first model changed. 
    cat claude-haiku-4.5/0/workspace.patch

    You should see: a patch like the one in "Reading a patch". Read the lines that begin with +. The 0 in the path is the first run for that model.

  10. Goal: read what the second model changed, and compare. 
    cat gpt-5.6-terra/0/workspace.patch
    +### Fixed
+- Fix the help text typo in `notes add` (#42)
+

    You should see: the same kind of patch with different added lines. Those above are ours. Compare the end of each model's entry.

  11. Goal: return to the practice folder. 
    cd ../../../../..

    You should see: nothing printed. The five ../ climb back up to practice.

What the two patches show

In our run, both models got a tick. One wrote an entry with no pull request number. The other ended its entry with (#42). Nobody mentioned a pull request 42. The entry above it in the file is #41, and the model made up the next number. In our runs, gpt-5.6-terra usually made up a number and claude-haiku-4.5 usually did not.

Your two models may differ in another way, or agree. Either result is evidence about your skill that trying it by hand would not have given you.

  2. The skill says "Reference the pull request." Write one sentence saying what you want the agent to do when the request names no pull request. Keep it: lesson 5 turns it into a rule in the skill.
    Show model answer

    There is no single right answer. One reasonable rule: "If no pull request number is given, leave the reference off. Never make one up." What matters is that the rule is stated, so that every model follows the same one.
