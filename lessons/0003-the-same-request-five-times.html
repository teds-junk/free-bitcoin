This lesson answers: If the same model gets the same request again, does it do the same thing?

One model invented a pull request number and one did not. It is tempting to conclude that the first model is the careless one and move on. But you have watched each model once. If you asked a colleague to do a task once and they made a slip, you would not know whether they slip every time or one time in ten, and those call for different responses. The same is true here, and finding out costs one extra word on the command line.

One run is one sample

A language model does not compute one fixed answer. It produces one of many plausible answers, and which one you get varies from run to run even when nothing else changes. An agent adds to this, because each step it takes depends on the step before.

So a single trial answers the question "can this happen?" and nothing more. The questions you care about for a skill are different: how often does it go wrong, and is that the same on each model? Those are counts, and a count needs several trials of the same stimulus.

The variation is not small. One 2026 preprint, a paper not yet reviewed by other researchers, ran the same agent several times on the same set of coding tasks. The share of tasks it completed moved by 2 to 6 percentage points from one identical run to the next.

Sources: Anthropic, Demystifying evals for AI agents, 2026-01-09; KTH, variance on SWE-bench Verified, 2026 (a preprint, one benchmark).

Trials and their four outcomes

Adding --runs 5 to vally eval runs every stimulus five times on every model you name. Each one is a separate trial in a fresh workspace, and each gets its own numbered folder: 0, 1, 2, 3, 4.

With several trials, a stimulus no longer just passes or fails. Vally sums up its trials with one of four words:

WordWhat happened across the trials
PASSEvery trial passed.
FLAKYSome trials passed and some failed.
FAILNo trial passed.
ERRORAt least one trial did not finish, so it has no verdict.

Two details will save you confusion. First, folders number trials from 0, but the lines Vally prints in the terminal number them from 1. "Trial 1" on screen is folder 0. Second, ERROR is not a kind of failure. It means the agent never produced an answer to judge, for example because its connection dropped. When you see ERROR, run the command again, or leave that trial out of your count and say that you did.

One more thing is saved for every trial, and you will need it when a patch is empty. An empty patch means the agent changed no file. The trial's record in results.jsonl keeps the agent's final reply, in a field named output, and the reply usually says why.

Sources: Vally docs, Scoring; trial numbering from our run on 2026-11-10 with Vally 0.21.0.

Why the course limits workers

Vally does not run trials one after another. It runs several agent sessions at once, and --workers sets how many. The default is five.

More sessions at once is faster, but each one holds an open connection to the model service, and those connections can drop under load. When we ran ten trials with the default five workers, three ended in ERROR with the message "Session disconnected while waiting for a response". With --workers 2, all ten finished. Two workers still drops a session now and then, so an occasional ERROR remains possible.

This course uses --workers 2 whenever a command starts more than a couple of trials. The cost is time: the ten trials in this lesson took about a minute in our run.

A stimulus runs five trials. Three pass, and two never finish because the connection dropped. Which word does Vally show for it?
Right. A trial that did not finish has no verdict, and one such trial is enough to mark the stimulus ERROR. Run it again.
It shows ERROR. FLAKY and FAIL describe trials that finished and were judged. A dropped connection produces no answer to judge, so the stimulus is marked ERROR and should be run again.

Optional: a scripting shortcut for the replies

Typed in the run folder, the one that contains results.jsonl, this prints the model, trial number and final reply from each record. It needs jq.

jq '{model, trialIndex, reply: .trajectory.output}' \
  results.jsonl

The part in braces builds a small object from three parts of each record: model and trialIndex as they are, and .trajectory.output under the name reply. The last object is all null: it comes from the summary record. Nothing in this course depends on this command.

What the tally says

Now you have counts in place of an impression. In our run, one model invented a number in one of five trials and the other did so in all five. That is a property of the skill on each model, and it is worth fixing in the skill.

Every trial that made up a number passed. The careful answer would be to change nothing and ask which pull request to cite, and that is the only kind of answer this grader fails. In lesson 5 one of our trials does exactly that. Keep it in mind; lesson 8 comes back to it.
