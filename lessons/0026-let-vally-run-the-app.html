This lesson answers: How do I give the app's own agent code Vally's trials, experiments and model comparisons?

Lesson 25 ended on a question it could not answer. On haiku, the release app's one run failed the same two graders as Vally's own trials: no skill loaded, and an entry for the refactor. Is the app as good as those trials, or worse, and does it cost the same? Grading afterwards cannot say, because each run of the app happens once. What you want is the app's own code, run as many times as you like, on any model, with everything else about the eval left as it is. Vally has a place to plug that in.

The executor is the seam

Lesson 17 introduced the executor: the part of Vally that runs the agent for each trial. Everything around it stays the same whichever executor you use. Vally prepares the workspace, runs the commands: setup, takes the starting state, runs the executor, saves the patch, runs the graders, repeats for every trial and model, and writes the report. The executor gets the stimulus and a workspace, and hands back a trajectory: a record of what the agent did.

Vally's own executor, copilot-sdk, opens a Copilot SDK session with Vally's choice of settings. The release app also opens a Copilot SDK session, with the team's choice of settings. Those choices are part of the feature you are testing. If the app's agent behaves differently from Vally's, an eval run through Vally's executor will not show it. Replace the executor with one that calls the app, and every trial runs the code the team ships, under every grader, budget and comparison you have built.

So there are now three ways to look at the release feature, and each answers something the others cannot:

  • Vally's own executor: does the skill do its job, on any model, separated from the app?
  • The app through an executor plugin: does the feature, as shipped, do its job? Repeatable, so you can count.
  • Grading the app's real runs afterwards (lesson 25): is it still doing its job in real use?

What an executor returns

An executor plugin is a JavaScript module. It exports one function, registerExecutors, which Vally calls with a registry; the function registers one or more executors. An executor is an object with three parts: a name, an execute function that runs one trial, and a shutdown function Vally calls at the end. The starter ships the plugin as app/vally-executor.mjs, with everything except execute written. Its top already imports what execute uses (path, randomUUID, Vally's computeMetrics and the app's writeEntries) and defines the two helpers it calls, toTrajectoryEvents and telemetryFor. The end looks like this:

  3. Nothing to clean up: the app opens and closes its own session in each trial.

execute receives the stimulus (its prompt is the request) and an options object. These are the options the release app needs:

Vally loads the plugin from .vally.yaml, the project file from lesson 21. A plugins section lists plugin files by kind:

.vally.yaml (the new lines, at the top)

  executor:
    - ./app/vally-executor.mjs

Loading the file does not select the executor. You choose it per run with --executor release-app, per eval file with defaults.executor, or per experiment with executor under overrides.

Joining the app's traces to Vally's

Vally records spans of its own for every trial, in otel-spans.jsonl in the run folder: a vally.trial span and, inside it, a vally.attempt span for each attempt. The app records its spans in its own file. In lesson 25 the app's invoke_agent span had no parent: each session was a separate trace. If both programs send their spans to the same tracing tool, you want the app's spans inside the trial's, so a slow or expensive trial can be opened and followed from Vally's step down to the model call.

Trace context

The ID of a trace and of the span that is currently open in it, passed from one program to another so that the second program's spans join the first one's trace as children. The W3C Trace Context standard writes it as a short string named traceparent: a version, the trace ID, the parent span's ID and some flags, joined by hyphens. An optional tracestate carries vendors' extra values.

Vally passes the trial's trace context to the executor as options.traceContext, an object with traceparent and tracestate. Its type's comment says executors "that spawn their own traced runtimes should propagate this context". The Copilot SDK takes a function, onGetTraceContext, that it calls before it opens a session or sends a message. So the app needed two lines:

Write and run the executor

You will fill in the executor, load it, run your release eval through it on both models, look at where the app's traces went, and then run an experiment with three trials per model. The experiment file is new. It is lesson 10's shape, with the executor set once for every variant:

  runs: 3

variants:
  haiku:
    overrides:
      model: claude-haiku-4.5
  terra:
    overrides:
      model: gpt-5.6-terra

  2. The same executor for both, set in the top-level overrides beside runs.

What you can now measure

Every tool from this course now applies to the feature as shipped. The same eval file ran unchanged: its setup command, hidden test and tool-calls graders did not know or care which executor ran. cost was filled in again, because the executor reports the runtime's own usage. Budgets from lesson 18, ranges from lesson 15 and comparisons from lesson 19 all work on these trials, since they are ordinary trials.

And the question lesson 25 could not answer now has counts. Your runs of since-last-release in lessons 22 and 23 went through Vally's own executor: five trials per model in lesson 22 and three in lesson 23, eight in all. (Lesson 24's run was filtered to tracker-down.) Here are ours beside the app's four per model, from the eval in step 4 and the experiment:

haiku, the app0 of 40 of 417,4312.14

"Passed" is each run's own verdict: lesson 22's run had only the hidden test, and lesson 23's added the checks on the steps. "Tokens a model call" is all of a row's trial tokens divided by all its model calls; each trial's trajectory.metrics in results.jsonl holds both, as tokenUsage.totalTokens and tokenUsage.callCount. "AIU a trial" is the row's total cost divided by its trials.

Two findings, and they need different amounts of caution.

The app behaves like Vally's runs of the skill. Terra loaded the skill and passed every time either way. Haiku rarely loaded it either way: 0 of 5 through the app, counting lesson 25's run, against 1 of 8 through Vally's executor in lessons 22 and 23. Put those in lesson 15's range calculator: 0% to 43% against 2% to 47%. The ranges overlap almost completely, so there is no sign that the app makes haiku worse. That is worth knowing: what you learned about the skill in lessons 22 to 24 holds in the app, and the fix belongs in the skill or the model choice, not in the app.

The app costs more per model call, every time. Divide each trial's tokens by its model calls: on haiku the app's lowest was about 17,300 and Vally's executor's highest about 15,200; on terra, 13,800 against 12,500. No trial broke the pattern. The app's traces show why. An MCP server is a program that offers an agent extra tools through a shared protocol, the Model Context Protocol. The app's sessions include GitHub's hosted one, which adds five GitHub tools to every request the model sees, and Vally's own executor turns that server off. That is about 16% more tokens a call on haiku and 12% on terra. A trial's cost also depends on how many calls it makes, and in our runs that hid the difference: the app's trials made fewer calls (4.75 a trial on haiku against 5.6, 4.5 on terra against 4.9) and cost slightly less, 2.14 AIU against 2.23 on haiku and 3.24 against 3.39 on terra. An earlier test of ours on a different request went the other way: 85k tokens and 3.27 AIU through the app, against 74k and 2.94 through Vally's executor. The extra cost of every call is steady; whether a whole trial costs more depends on the trial. An eval of the skill alone would not have shown that overhead at all.

Neither finding could be counted from the app's real runs, and the second was invisible from inside Vally's own executor. That is the reason to plug the app in: the eval now measures what the team ships.

The team turns off the hosted GitHub MCP server in the app. How would you check that it helped, and did no harm?
Right. The same graders, on the app's own code, with several trials of each version and both models, side by side as in lesson 15. Grading real runs afterwards then checks that it holds in use.
Run the experiment again, before and after the change, on the app's own code. Vally's own executor never ran the app's settings, real runs cannot be repeated, and one run against one run is the small sample lesson 15 warned about.

Exercises

  1. From memory, say what an executor plugin exports, what execute receives and what it returns.
    Show model answer

    It exports registerExecutors(registry), which registers an object with a name, execute and shutdown. execute receives the stimulus and options such as the workspace, model, skills, time limit and trace context. It returns a trajectory: the events (tool calls, skill loads, token usage, messages), the final output, the workspace, metrics from computeMetrics plus the wall time, and metadata.

  2. Why does the executor pass options.traceContext to the app instead of letting the app start its own trace?
    Show model answer

    So the app's spans become children of the trial's span in one trace. In a tracing tool you can then go from a trial Vally ran, down to every model call and tool call the app made for it. Without it, the app's session is a separate trace with nothing tying it to the trial.

  3. Add disabledMcpServers: ["github-mcp-server"] to the app's createSession options and run the experiment again. What do you expect to change? (This spends six agent runs. We have not run this, so we cannot show a result.)
    Show model answer

    Fewer tokens per model call, close to the numbers through Vally's own executor, since the five GitHub tools leave every request. Whether haiku then loads the skill more often is the open question; count it, and use lesson 15's ranges before believing a change.
