This lesson answers: Does the skill still hold when the conversation continues?

Nobody uses an agent one request at a time. They ask for a changelog entry, then remember a second change, then a third. Every stimulus you have written starts a fresh conversation with a single request, which is the one situation real use rarely looks like. In a conversation the agent remembers what came before, and that memory is a new source of mistakes. This lesson tests a conversation of three requests, and finds a failure that no single request could have produced.

What changes in a conversation

Each request in a conversation is called a turn. When a conversation continues, the agent keeps two things from the earlier turns: the workspace as it left it, and its memory of what was said. Three things can then go wrong that cannot go wrong in a single request.

  • A rule fades. The skill was loaded at the start. Several turns later the model follows the pattern of its own recent work more than the rules.
  • An earlier turn leaks into a later one. A detail from the previous request, such as a pull request number, is carried into a change it has nothing to do with.
  • A later turn disturbs earlier work. While adding the third entry, the agent rewrites or drops the first.

A grader that looks only at the final file cannot tell you which turn went wrong, and can miss the second kind of failure entirely. So a conversation is graded turn by turn: for each request, what did the agent change in response to that request alone?

One limit to know before you design a conversation. Vally sends the follow-up requests you wrote, in order, whatever the agent replied. It does not play a user who reacts, and its documentation describes no way to make it. So you can test how the skill copes with a script of requests, and not with a user who answers back.

Turns, and graders scoped to a turn

A stimulus can have turns: in place of prompt:. It is a list of requests. Vally sends the first, waits for the agent to finish, sends the second to the same session, and so on. The agent keeps its workspace and its memory throughout. One conversation is one trial.

A grader can then be limited to one turn by adding turn: and a number. Vally's documentation calls such a grader scoped to a turn. Turns are numbered from 0. A diff grader with turn: 2 sees only what the agent changed during the third request. A grader with no turn: sees the whole conversation, as before.

Not every grader can be limited this way. The three diff graders can, and so can graders that read the agent's events, such as skill-invocation. A script grader cannot: it sees only the workspace as it is at the very end.

The starter folder has a conversation of three requests, each chosen to lean on a different rule of your skill. Here it is with the graders you will add.

evals/conversation.eval.yaml (the stimulus)
  - name: three-requests
    turns:1
      - |
        PR 64 is merged: `notes delete` now asks for
        confirmation before it deletes anything. Update
        the changelog.
      - |2
        One more, PR 65: I renamed some internal helper
        functions. Add that too.
      - |3
        I also fixed the exit code of `notes export` when
        the disk is full. Record that as well.
  1. A list of requests. Each - | starts one.
  2. An internal change. By your skill's rule, the right response is to add nothing.
  3. A fix with no pull request number, arriving just after two requests that had one.
evals/conversation.eval.yaml (graders to add under the turns)
    graders:
      - type: diff-contains
        name: first-adds-64
        turn: 01
        config:
          pattern: '(?m)^\+.*\(#64\)'
      - type: diff-empty
        name: second-adds-nothing
        turn: 12
      - type: diff-contains
        name: third-adds-entry
        turn: 2
        config:
          value: "notes export"
      - type: diff-not-contains
        name: third-no-made-up-number
        turn: 23
        config:
          pattern: '(?m)^\+.*\(#\d+\)'
      - type: diff-contains
        name: first-entry-survives4
        config:
          pattern: '(?m)^\+.*\(#64\)'
  1. turn: sits beside type and name, not inside config. In the first turn the agent must add a line citing (#64).
  2. In the second turn it must change nothing.
  3. In the third turn it must add no line that cites any pull request. The pattern is the one from lesson 5.
  4. No turn:, so this reads the whole conversation: by the end, the first entry must still be there.

Vally saves a diff for every turn of every trial, in a folder named diffs inside the run folder. The file names end with the trial and turn numbers, such as trial-1__turn-2.diff.

Write and run a conversation

You will add the graders, run the conversation three times on each model, read the diff of a turn that failed, add a rule to the skill, and run again. This is the rule, for step 6:

skills/changelog-entry/SKILL.md (lines to add at the end)
- Treat every request on its own. A pull request number
  belongs only to the change it was given with. Never carry
  one over from an earlier request.

Three requests, graded one at a time

  1. Goal: read the conversation. Open a terminal in practice. 
    cat evals/conversation.eval.yaml

    You should see: one stimulus with three requests under turns:, and no graders.

  2. Goal: add a grader for each turn. This edits one file. In evals/conversation.eval.yaml, add the graders shown above at the end of the stimulus, with graders: lined up under turns:.
  3. Goal: catch mistakes before spending anything. 
    vally lint -e evals/conversation.eval.yaml

    You should see: the usual one warning and no errors.

  4. Goal: run the conversation three times on each model. This spends six agent runs of three requests each, and takes about a minute. 
    vally eval -e evals/conversation.eval.yaml \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --runs 3 --workers 2 \
  --output-dir results/lesson-11
    claude-haiku-4.5
  FLAKY  three-requests  1 passed · 2 failed
   ✘ third-no-made-up-number  1 passed · 2 failed

    You should see: a summary, and a block like this for any model that did not pass all three conversations. The grader's name tells you which turn failed and how. This is ours.

  5. Goal: read what the failing turn changed. Find the run folder, move into it, print the diff of that turn, and come back. In our run the terminal named trials 1 and 2 of the first model. File names count from 0, so the second of those is trial-1, and the third turn is turn-2. The * stands for the start of the file's long name. Use your own folder, model, trial and turn. If none of yours failed, read any third turn. 
    ls results/lesson-11
    cd results/lesson-11/2026-11-10T15-04-14-517Z
cat diffs/*haiku-4.5__trial-1__turn-2.diff
cd ../../..

    You should see: a short patch holding only what that one turn changed. Ours is shown after the checkpoint.

  6. Goal: close the gap in the skill. This edits one file. Add the three lines shown above the checkpoint to the end of skills/changelog-entry/SKILL.md.
  7. Goal: run the conversations again. This spends another six agent runs. 
    vally eval -e evals/conversation.eval.yaml \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --runs 3 --workers 2 \
  --output-dir results/lesson-11-after
      eval          claude-haiku-4.5  gpt-5.6-terra
  conversation  ✓ 1/1             ✓ 1/1

    You should see: your own summary. In ours, all six conversations passed.

What the conversation showed

This is the line our failing turn added, under the Fixed heading:

+- Fix `notes export` exit code when disk is full (#65)

Look closely at it. The third request gave no pull request number. The entry cites (#65). That number is real: it belongs to the second request, the internal rename, which the agent had correctly left out of the changelog a moment before. The number was not invented. It leaked from one turn into the next, and attached itself to a different change.

This happened on the model that made up a number in a single request only once in every lesson so far, in lesson 3. In another of our conversations the same model cited (#66), a number nobody gave. A test of single requests would have called that model nearly safe on this point. And a grader reading only the final file would have seen a tidy, well-formed entry with a plausible reference.

The fix was one more rule, and with it all six conversations passed. Two failures in three becoming none in three is, once again, a small sample.

There is something this lesson's graders did not check, and we are leaving it alone for now. In one of the other model's conversations, the first entry, a change in behaviour, was filed under Fixed. Whether that is the right category is a judgement about meaning, and so is the question lesson 4 left open: is an entry written for the people who use the tool? No pattern can decide either. The next lesson takes up the second.
