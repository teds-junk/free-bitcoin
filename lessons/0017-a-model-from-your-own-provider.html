Answer from memory before reading on.

  1. What does reasoning_effort set, and why could one model accept a value that another refuses?
    Show answer

    How much the agent's model reasons before it replies or calls a tool. The accepted values depend on the model: in lesson 16, claude-haiku-4.5 refused any effort while claude-haiku-5.5 took one.

  2. Why compare cost per passing trial rather than cost per trial?
    Show answer

    Every trial is paid for, useful or not. A cheap model that fails often can cost more for each useful result than a dearer one that passes, and dividing the total cost by the passing trials shows that.

This lesson answers: My app calls a model through its own provider, not my Copilot account. Can Vally run that same model?

Every trial so far has gone through your Copilot account: Vally asked for a model by name, the account served it, and the trial recorded what it cost. The notes-cli team's release tool, which part 2 of the course looks at after lesson 21, may not work that way. Teams often call a model through a provider they pay directly, or one they run themselves, for reasons of price, data rules or speed. If that is the model your skill will meet, it is the model to evaluate. In this lesson you point one variant of lesson 16's experiment at a model running on your own computer, and work out what its trials would cost.

Evaluate the model you ship

Lesson 1 showed two models reading the same skill two ways. Less obviously, one model served two ways can behave differently too. Whoever serves a model decides how it is stored (often compressed to fit smaller machines: the copy we used in this lesson is a 4-bit compressed version), how the conversation and the agent's tool calls are turned into the text the model reads, and which default settings it runs with. Each of those can change what the agent does. So a result for "the same model" from somewhere else says little about yours, even when the name matches.

We met this while preparing the lesson. The first local model we tried, gpt-oss:20b, failed every trial before it changed a file: the server answered 400 invalid tool call arguments. The model may well be able to write a changelog entry. The way this server passed its tool calls to the agent did not work, and only a run through that endpoint could show it.

So evaluate through the endpoint the app uses, with the model name the app sends. Keep the stimuli, graders and skill the same, so that the results line up with every other variant.

Bring your own key

Executor

The part of Vally that runs the agent for each trial: it starts a session, sends the stimulus, and records what happened. Unless a file says otherwise, Vally uses its built-in executor, copilot-sdk, which reaches models through your Copilot account.

Bring your own key

Having the executor call a model provider you choose, with your own credentials, instead of your Copilot account. The Vally docs call it BYOK.

The executor is set under defaults in an eval file, or under overrides in an experiment variant. To bring your own key, give it a config holding a provider block. This one is for a hosted provider. We checked it with vally lint; we did not run it.

an eval file's defaults, for a hosted provider
defaults:
  model: my-model-name1
  executor:
    name: copilot-sdk2
    config:
      provider:
        baseUrl: https://api.example.com/v13
        type: openai4
        apiKeyEnv: MY_PROVIDER_KEY5
  1. The name the provider knows the model by. Vally does not check it against your account's list of models, as it does for Copilot models.
  2. Still the built-in executor. Only where it sends the model's requests changes.
  3. The provider's address. The only required field.
  4. The kind of interface the provider offers. openai is the default, and many servers other than OpenAI's offer that kind, Ollama among them.
  5. The name of an environment variable that holds the key, not the key itself. Vally reads it from the environment of the vally command when each trial starts.

The key never goes in the file, because eval files are shared and kept with results. Vally enforces this: there is no field for a key, and lint rejects one. This is lint on a copy of the file above with apiKey: abc123 in place of line 5:

✘ error [executor-config-invalid]
  defaults.executor.config.provider has unknown
  field 'apiKey' (allowed: type, baseUrl, wireApi,
  transport, apiKeyEnv, bearerTokenEnv, azure, headers,
  modelId, wireModel, maxPromptTokens, maxOutputTokens)

The other allowed fields serve providers with their own conventions, such as Azure's deployment names; the primary source below describes each. If the variable is not set when you run, lint still passes, but every trial stops with ERROR before the agent starts. Ours:

ERROR  hello
 defaults.executor.config.provider.apiKeyEnv
 references environment variable "MY_PROVIDER_KEY",
 but it is not set. Export MY_PROVIDER_KEY with your
 provider credential before running.

A model on your own computer needs no key. Ollama, a free program that downloads open models and serves them on your machine, answers at http://localhost:11434/v1 with the openai kind of interface, so a provider block with only baseUrl is enough.

What a trial records changes in one way. Its tokens are counted as before, in tokenUsage. Its cost is absent: as lesson 16 said, Vally records a cost only when every call in the trial reported one the Copilot way. You price the tokens yourself, at your provider's rates. A variant on a local model

The checkpoint adds a fifth variant to lesson 16's experiment, qwen-local, which runs qwen3.5:9b through Ollama on your computer. It is a small open model that can call the agent's tools, and the one that worked for us. Three of its settings differ from the other variants, so vary gains three paths. Without /defaults/executor among them, the dry run stops with Experiment drift detected, as lesson 10 described.

evals/cost.experiment.yaml (after this lesson)
vary:
  - /defaults/model
  - /defaults/reasoning_effort
  - /defaults/executor1
  - /defaults/timeout
  - /defaults/runs
23 lines hidden: baseline, overrides and lesson 16's four variants
  qwen-local:
    overrides:
      model: qwen3.5:9b
      timeout: 9m2
      runs: 13
      executor:
        name: copilot-sdk
        config:
          provider:
            baseUrl: http://localhost:11434/v14
  1. The same list as lesson 16's one-line vary, written one path per line, with three new paths: the executor, the time limit and the number of trials may now differ between variants.
  2. A local model is slow. Our trials took two to three and a half minutes, and one took five and a half in an earlier run, so the limit is nine minutes instead of the eval file's three.
  3. One trial of each stimulus instead of three, so the run takes about a quarter of an hour. This variant's count comes from fewer trials than the others'; the last section takes that into account.
  4. Ollama's address on your computer. No key, so no apiKeyEnv.

Run it with one worker, not the course's usual two. Our local server answered one request at a time, so with two workers each trial waited on the other: in our first attempt, both trials ran out of their nine minutes and ended in ERROR ("timed out after 540000 ms").

To price the tokens, this lesson uses a price we made up for the arithmetic: $0.10 per million input tokens and $0.40 per million output tokens. It is not any provider's price. Your real prices are on your provider's pricing page or in your contract; check there too whether input read from cache is charged less.

Run a variant on your provider

You will install Ollama, add the variant shown above, run it on its own, and price its tokens. This checkpoint is optional. It needs Ollama, about 7 GB of disk for the model, and enough memory to run it: Ollama used about 10 GB on our 32 GB computer. It costs nothing in Copilot usage. If you skip it, read our output at each step.

What changed

A good deal carried over unchanged. The same eval file, stimuli, graders and skill ran; the trial folders, patches, report and results.jsonl had the shape you know; the calculator read the file as it reads lesson 16's. Changing the provider was a few lines in one variant, and every tool from the earlier lessons still applied. That is the payoff of evaluating through the endpoint: nothing else has to change.

The results did not carry over. Our local model passed 2 of 5, where lesson 16's variants passed every trial that finished. Its patches read like lesson 4's list of failure modes: the security fix filed under Fixed, an entry for the internal refactor, and a new entry added to the 1.3.0 release that had already shipped. The trial records show why: the skill was in the workspace, but none of the five trials activated it. Everything lessons 5 to 15 taught the skill, this model never read. Lesson 9's question, does the skill load, comes back with each new model.

Is 2 of 5 too few trials to say anything? Apply lesson 15's habit. Two passes in five gives a range of 12% to 77%. haiku-low's 15 in 15 gives 80% to 100%. The ranges do not overlap, so even five trials show this model doing worse on these stimuli. A count that low settles "worse"; it would take many more trials to say by how much.

Cost did not carry over either. Run locally, the tokens cost nothing, though the trials took two to three and a half minutes each against seconds through Copilot, and they used the computer's memory the whole time. Priced at our made-up hosted rate, the variant came to about 1.6 cents per passing trial: over seven times haiku-low's 0.2 cents, though below terra-low's 2.7. Two things drove that, and neither is the price per token: three of five trials failed, and with nothing read from cache every turn paid for the whole conversation again. That is lesson 16's point from the other side: a low price per token is not a low cost per passing trial.

Keep the scope in mind. This is one model, served one way, on one computer, with a price we invented. The same model from a hosted provider might load the skill, cache its input, or be priced differently, and the first section says why you cannot assume any of that. The method is what carries over: run the endpoint your app uses, read the tokens, price them at your own rates, and divide by the passes.

Exercises

  1. From memory: where does Vally find the key for your own provider, and why is the key never in the eval file?
    Show model answer

    In an environment variable of the vally command, named by apiKeyEnv in the provider block. Eval files are shared and kept with results, so a key written there would leak; Vally has no field for one, and lint rejects apiKey.

  2. A teammate says: "The local model is free, so it is the cheapest choice for lesson 16's five stimuli." Answer with this lesson's numbers.
    Show model answer

    Free per token, but it passed 2 of 5 where haiku-low passed 15 of 15, and the ranges (12% to 77% against 80% to 100%) do not overlap. Each trial took minutes and the machine's memory. Priced as if hosted it came to about 1.6 cents per passing trial against haiku-low's 0.2. Free tokens do not make a passing trial cheap.

  3. Your app actually calls a hosted provider at https://api.example.com/v1, with its key in a variable called RELEASE_APP_KEY. What do you change in the qwen-local variant, and what must you do before running it?
    Show model answer

    Rename the variant, set model to the name the app sends, set baseUrl to the provider's address, add apiKeyEnv: RELEASE_APP_KEY (and type if the provider's interface is not the openai kind), and put timeout and runs back to the other variants' values if the provider is fast. Before running, set RELEASE_APP_KEY in the terminal where you run vally; otherwise every trial stops with ERROR. Then price the tokens at the provider's real rates.
