When a run goes wrong

    Show answer

    FAIL is a verdict: the agent finished and a grader said no. ERROR is not a verdict: the trial did not produce a result that could be graded, so it says nothing about the skill either way.

  2. What does --workspace keep, and when do you need it?
    Show answer

So far: You can measure the skill, price it, set budgets, and gate on a regression with vally compare.

This lesson answers: When a run ends in ERROR, FLAKY or a surprising FAIL, how do I find out why without paying for more runs?

The eval files now have setup, budgets, judges and several models, so more of them can go wrong in ways that have nothing to do with the skill. When a run goes wrong, running it again is tempting: it feels like doing something. But a run costs agent runs and minutes, and it usually prints the same error again. Nearly every answer you need is already on disk, in the console output and the run folder. This lesson gives you the order in which to look, and four broken eval files to practise on. Each fails for a real reason that we hit while writing it.

Four questions, cheapest first

Vally's Debugging Evals guide splits debugging into four steps. Each is a question, and each must be answered before the next one means anything. A grader cannot be wrong about a trial that never finished, and a trial cannot finish if the eval file is broken.

  1. Is the eval valid? Does Vally accept the file at all: known field names, files that exist, values of the right kind?
  2. Did it complete? Did each trial finish and get graded? An ERROR belongs here.
  3. Why was the result unexpected? The trial finished but the verdict surprised you: a FAIL you did not expect, or a FLAKY stimulus. Decide whether the agent or the grader is wrong.
  4. Does the fix work? Prove it with the cheapest check that can show it.

The order is also an order of cost. The first three questions are answered by reading what the failed run left behind, which costs nothing. The fourth sometimes needs a new run, and the habit to build is to ask what a fix changed. A fix to a grader changes nothing the agent did, so the saved trials can be graded again. A fix to the setup or the time limit changes the run itself, so it needs a new run, and often one model is enough to prove it.

Key idea

Before running anything again, read what the failed run already saved. Re-run only when the fix changes something that happens before or during the agent's session, and then with as few trials as will show it.

Source: Vally docs, Debugging Evals (the four steps; fetched 2026-11-10 for Vally 0.21.0).

Where each answer lives

Question 1: what lint checks, and what it cannot

vally lint (lesson 2) reads an eval file without starting anything. It reports field names it does not know, files that do not exist, and values whose kind the format forbids. vally eval runs the same checks before starting any agent. What neither can see is what a value means to the program that will use it later. Lint checks the shape of the file. It does not run each value to see whether it works.

One of this lesson's files uses a field the course meets properly in lesson 22. It is introduced here because a mistake in it is the clearest case of a file that lints clean and still cannot run.

commands:

A list, under agent_environment, of shell commands Vally runs in the workspace after copying the files and before the agent starts. Each entry is one command, written as a string. What the commands create is part of the starting state, so it does not appear in the trial's diff.

agent_environment:
  commands:
    - echo hello > note.txt

The trap is in YAML itself. Inside a list item, a colon followed by a space turns the line into a key and a value. - echo note: hello is not the string echo note: hello. It is a small mapping whose key is echo note and whose value is hello. Lint accepts it, because a list item may hold a mapping. The program that runs the command receives a mapping where it expects a string, and says so in its own words. Putting the whole line in quotes makes it a string again.

Question 2: ERROR lines and the trial folder

A trial that did not complete is reported as ERROR with one line of explanation, in the block for its stimulus and again under Failures. The same text is saved in the trial's record in results.jsonl, as error, beside status and durationMs, the trial's length in milliseconds.

The trial's own folder (lesson 2) tells you how far it got, by which files exist. These are from our runs:

The trial folder holdsWhat it means
metadata.json onlyNo agent session started. The failure came during setup.
events.jsonl, no workspace.patchThe agent started and was stopped before it finished.
events.jsonl and workspace.patchThe agent finished. Anything wrong is in the grading or the work.

The session log, events.jsonl, is the agent's raw record, one event per line, in the runtime's own words. It is not the trajectory. Vally builds the trajectory from it, renames the events, and saves the trajectory in results.jsonl; that is where graders and lesson 9's skill_activation event live. The raw log matters here because, for a trial stopped mid-session, it holds the one record of what the trial cost (note 3 below). When a trial runs out of time, the log ends like this. The lines are shortened here to the fields that matter:

…/quick/typo-fix/gpt-5.6-terra/0/events.jsonl (end)
{"type":"skill.invoked", …}1
{"type":"assistant.turn_end", …}
{"type":"assistant.turn_start", …}
{"type":"abort","data":{"reason":"user_initiated"}, …}2
{"type":"assistant.turn_end", …}
{"type":"session.usage_checkpoint",
 "data":{"totalNanoAiu":1255180000, …}, …}3
  1. How far the agent got: it had loaded the skill and was starting its next step. skill.invoked is the runtime's name for a skill loading; the trajectory records the same moment as skill_activation (lesson 9).
  2. Vally stopped the session. "User initiated" means the stop came from outside the agent, here from Vally's time limit.
  3. What the session cost before it was stopped: 1,255,180,000 nano-AIU, which is 1.26 AIU. A trial that ends in ERROR is not free, and this is the only place its cost is written: its record in results.jsonl has no cost.

Question 3: evidence, --verbose and the patch

For a trial that finished, start with the grader's evidence: the line Vally prints after each failing grader, such as Pattern … not found in workspace diff. Then read the trial's workspace.patch yourself, as in lesson 4, and decide who is wrong: the agent or the grader.

--verbose

A flag that asks a command for more detail. On vally eval, it adds, under each failing trial, the number of turns, tool calls and tokens, and the agent's final reply. On vally grade and vally oracle, it prints every grader's evidence or reason, including for graders that passed (lessons 7 and 12).

The docs add that in a run with several trials of each stimulus, --verbose shows the agent's reply only for failing trials. A passing trial's reply is in results.jsonl. A trial stopped mid-session has no final reply, so --verbose adds nothing to a timeout.

A grader can also fail to produce a verdict at all. A judge is a call to another model, and that call can fail. Vally does not retry it. The grader is recorded with status error, a score of 0, and the error as its evidence, and the stimulus is reported as ERROR with Grading error; verdict is invalid. This is the judge's entry from one of our trial records, with the account's list of models shortened:

results.jsonl (one grader in gradeResult.details)
{
  "name": "users-words",
  "status": "error",1
  "kind": "llm",
  "passed": false,
  "score": 0,2
  "evidence": "LLM judge failed: Model
    \"claude-sonnet-5-5\" is not available in
    Copilot. Available models: auto, …",3
8 lines hidden: label, metadata, type, name
}
  1. The grader did not reach a verdict. A grader that ran and said no has no status field at all.
  2. A grader that said no also scores 0, so the score alone cannot tell the two apart. Here the 0 is a placeholder, not a judgement of the trial.
  3. The reason, word for word. It is wrapped here to fit the page; in the file it is one line. The hidden lines hold the label, the judge model and the same error again under metadata, and the grader's type and name.

Question 4: what a re-grade can and cannot read

  • vally grade (lesson 8) runs the eval file's current graders on saved trials. Diff graders read the saved diffs and trajectory graders the saved trajectories, so a re-grade with them costs nothing. A judge re-grade costs one judge call per trial and no agent runs.
  • File and script graders read the workspace, which a saved run does not keep. When we re-graded a saved run with a file-contains grader, every trial ended in ERROR with Grader error: Directory '…' does not exist. Only a new run with --workspace keeps a folder they can read.
  • A new run is the only thing that shows a change to anything before or during the agent's session: the setup, the time limit, the skill. It costs one agent run per trial per model.
A trial ends in ERROR after 9 ms, and its folder holds only metadata.json. What does that tell you first?
Right. With no events.jsonl there was no session. The cause is in the setup, so look at the error text and at the eval file's environment, not at the skill.
No agent session ever started. A timeout or a grader needs a session first, and a session leaves an events.jsonl. With only metadata.json, the failure came during setup.
Sources: Vally docs, Debugging Evals (--verbose on multi-trial runs; judge calls not retried); Vally CLI reference; the folder contents, log lines and record are from our runs on 2026-11-10 with Vally 0.21.0.

Fix four broken evals

The starter has four eval files in evals/broken/, each with one fault. For each, run it once, answer the four questions from what the run left, fix it, and prove the fix with the cheapest check. In our run the four took nine agent runs and two judge calls. Your trials will differ from ours in wording and timing; the errors should match.

An eval that never starts an agent

  1. Goal: get the four broken files. This creates a folder. Open a terminal in practice. 
    cp -R ../practice-starter/evals/broken evals/broken

    You should see: entry.eval.yaml, judged.eval.yaml, merged-list.eval.yaml and quick.eval.yaml in evals/broken.

  2. Goal: question 1, is the first file valid? This is free. 
    vally lint -e evals/broken/merged-list.eval.yaml

    You should see: ✔ evals/broken/merged-list.eval.yaml is valid. In our run all four files passed lint. judged.eval.yaml also printed ⚠ warning [scoring-defaults-applied] Multiple graders with no scoring config, the warning from lessons 5 and 14: it has several graders and no scoring block, so every grader must pass. It is not an error.

  3. Goal: question 2, does it complete? This starts two trials. In our run neither reached an agent. 
    vally eval -e evals/broken/merged-list.eval.yaml \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --workers 2 --output-dir results/lesson-20

    You should see: ERROR from-the-list for each model, with The "command" argument must be of type string. Received an instance of Object. Ours also printed EvalMarkdownReporter threw: TypeError: text.replace is not a function and a stack trace: the same bad value broke the report writer, so no eval-results.md was saved.

  4. Goal: see how far the trials got. This is free. 
    ls results/lesson-20

    You should see: one folder named with the time of your run, such as ours, 2026-11-10T17-46-54-086Z. Use your folder's name in place of ours below.

    cd results/lesson-20/2026-11-10T17-46-54-086Z
ls merged-list/from-the-list/claude-haiku-4.5/0

    You should see: metadata.json and nothing else. No session started. In results.jsonl the trial's durationMs was 9 for one model and 11 for the other in our run. Return to practice with cd ../../...

  5. Goal: question 3, find the cause. Open evals/broken/merged-list.eval.yaml and read its commands: entry. What did YAML make of it?
    Show the cause

    The entry is - echo fix: notes add said tittle > merged.txt. The : after fix makes it a mapping with the key echo fix, so Vally was handed an object where it needed a command string. Lint passed it because a list item may be a mapping.

  6. Goal: fix it. This edits one file. Replace the entry with this line, keeping its indentation, so the whole command is one quoted string: 
    - 'echo "fix: notes add said tittle" > merged.txt'
  7. Goal: question 4, prove the fix. The fix changed the setup, so it needs a run. One model is enough: one agent run. 
    vally eval -e evals/broken/merged-list.eval.yaml \
  --model claude-haiku-4.5 \
  --workers 2 --output-dir results/lesson-20

    You should see: Summary and PASS merged-list. In our trial the agent read merged.txt and added - Fix notes add said title under a new ### Fixed. The setup works now. The entry itself is the note with its spelling corrected, not an entry a user could act on, which the loose grader in this file does not catch: a different question from this lesson's, and the kind of thing lesson 12's judge is for.

A grader that fails good work

  1. Goal: run the third file, with the agent's replies shown. This spends two agent runs. 
    vally eval -e evals/broken/entry.eval.yaml \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --workers 2 --output-dir results/lesson-20 \
  --verbose

    You should see: FAIL typo-fix for both models, each with ✘ adds-an-entry Pattern /^\+.*notes add/ not found in workspace diff. Under each, --verbose adds lines like these, from ours:

       5 turns · 4 tools · skill×1 · 75.4k tok
   74.7k in · 691 out

   agent output

    followed by the reply. Ours: Done! Added the typo fix to the changelog under the "Fixed" category in the Unreleased section.

  2. Goal: question 3, decide who is wrong. This is free. Use the newest folder, ours 2026-11-10T17-48-20-854Z. 
    cd results/lesson-20/2026-11-10T17-48-20-854Z
    Open entry/typo-fix/claude-haiku-4.5/0/workspace.patch.

    You should see: an added line such as ours, +- Fix typo in help text for `notes add`, under an added +### Fixed. That is a correct entry, and it contains notes add. So the grader is wrong.

  3. Goal: find the fault in the grader. Open evals/broken/entry.eval.yaml and read the pattern.
    Show the cause

    '^\+.*notes add' has no (?m). Without it, ^ matches only the very start of the patch, which is diff --git, so the pattern can never match. Lesson 8 met the same mistake in a diff-not-contains grader, where it meant the grader could never fail. In diff-contains it means the grader can never pass.

  4. Goal: fix it. This edits one file. Change the pattern line to: 
    pattern: '(?m)^\+.*notes add'
  5. Goal: question 4, prove the fix on the saved trials. No agent runs. From the run folder: 
    vally grade \
  -e ../../../evals/broken/entry.eval.yaml \
  --run-dir . < results.jsonl

    You should see: two blocks, each ✅ typo-fix (1/1 graders passed) and Score: 100.0% | PASSED. Return to practice with cd ../../...

A symptom table to keep

The four faults had something in common: none of them was about the skill, and none needed the agent to run again unless the fix changed the run itself. Two of them looked like results. A grader that cannot pass prints FAIL in the same place as a real failure, and a failed judge call prints a score of 0. That is why the order matters. Settle whether the eval is valid and whether it completed before you believe what any verdict says.

The table below collects what each symptom usually means. Rows marked "ours" come from runs in this course; rows marked "docs" come from the Debugging Evals guide and have not been met in our runs.

And a failed judge call is not retried: if a judge failed because its service was briefly unavailable, the trials are still on disk and a re-grade is the retry.

Exercises

  1. From memory, list the four questions in order, and for each say where its answer usually lives.
    Show model answer

    Is the eval valid: vally lint and the first lines of the run. Did it complete: the ERROR lines and the trial folder, including the end of events.jsonl. Why was the result unexpected: the grader's evidence, --verbose, and workspace.patch. Does the fix work: vally grade on the saved trials, or one new run when the fix changes the run itself.

  2. A teammate's grader is file-contains with value: "Notes add". Every trial fails it, and the patches show entries containing notes add. They fix the value. What is the cheapest proof, and why not vally grade?
    Show model answer

    file-contains reads the final file in the workspace, and a saved run keeps only the diff, so a re-grade ends in ERROR with Directory '…' does not exist. Either change the check to a diff grader such as diff-contains with value: "notes add" and re-grade for free, or re-run one trial on one model.

  3. One stimulus out of six ends in ERROR with "Session disconnected while waiting for a response", and the other five pass. Which question does this belong to, and what do you do?
    Show model answer

    Question 2: the trial did not complete, so it says nothing about the skill. Check the run used --workers 2, then re-run that one stimulus, or report five results and say that one trial did not finish.
