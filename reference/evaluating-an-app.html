Evaluating a skill inside an app

Verified 2026-11-10 · Vally 0.21.0 · Copilot SDK 1.0.30

How to put an app's agent under the graders you already have: start the agent where the app would, check the steps the app depends on, make a tool fail, grade the app's own runs, and let Vally run the app. The examples are the course's release app, in practice-starter/app/.

Three ways to look at the feature

WayAnswersGives upLesson
Vally's own executor, copilot-sdkDoes the skill do its job, on any model, apart from the app?The app's own settings22–24
The app as an executor plugin, inside VallyDoes the feature, as shipped, do its job? Repeatable, so you can count and compare models.Real inputs: Vally gives it the stimulus26
Grading the app's real runs after the factIs it still doing its job in real use?Repetition: each run happens once, on one model25

Most teams want both of the last two: trials inside Vally to decide whether a change is safe, and grading of real runs to see whether that still holds.

Start the agent where the app would

The stimulus is the app's situation: the files the app's checkout has, and what the app's own setup step produces. commands: runs in the workspace after the files are copied and before the agent starts. What they create is part of the starting state, not the diff. Quote every entry: an unquoted : makes a mapping (troubleshooting). Each command has 60 seconds unless commandTimeout says otherwise. Lesson 22

stimuli:
  - name: since-last-release
    prompt: >-
      Write the Unreleased changelog entries for every
      change listed in release/merged.txt.
    agent_environment:
      commands:
        - "mkdir -p release"
        - "node tools/list-merged.mjs > release/merged.txt"

git: builds the workspace from a repository instead (type: worktree with a ref and source, or type: clone). We did not run it.

A hidden test: a run-command grader passes when its command exits 0 (or expected_exit_code); stdout_contains and stdout_matches add checks; 30 seconds by default. Stage the test through grading_environment so the agent never sees it. Lesson 22

    grading_environment:
      files:
        - src: grading/check-release.mjs
          dest: .vally-grading/check-release.mjs
    graders:
      - type: run-command
        name: every-change-handled
        config:
          command: node .vally-grading/check-release.mjs

Check the steps the app depends on

Grade the outcome by default. Grade the route only for a step the app relies on (required), one with effects outside the workspace (forbidden), or a route that is too long. Keep a route grader as loose as the requirement: match "read the list", not one tool. Lesson 23

      - type: tool-calls
        name: reads-the-list
        config:
          required:
            - name: ^(view|bash)$
              pattern: release/merged\.txt
      - type: tool-calls
        name: never-commits
        config:
          disallowed:
            - name: ^bash$
              command: git (commit|push)
      - type: max-repeat
        name: no-loop
        config:
          max: 3
      - type: skill-invocation
        name: loads-the-skill
        config:
          required: [changelog-entry]

A tool-calls entry takes name (a pattern for the tool), and command, path or pattern for its arguments. These graders read the trajectory, so they re-grade a saved run for free. Lesson 23, loops

Make a tool fail

Decide what good behaviour is on a bad day (write nothing, say why, stop after a retry or two), then fail the tool on purpose and make that the only thing tested. Take the answer out of the workspace too, or the stimulus tests whether the agent finds another way to it. Lesson 24

- name: tracker-down
  tags: { case: tool-fails }
  simulation:
    tool_overrides:
      shell:
        patterns:
          - match: list-merged
            output: "error: tracker did not answer (timeout)"
            is_error: true

Grade it with diff-empty (writes nothing), loop-outcome with should_loop: false and max_acceptable_retries, a tool-calls requirement that it tried, and a judge for the reply. Run only these stimuli with --tag case=tool-fails. vally simulate record builds overrides from a saved run. Only executors that support simulation can run the block; copilot-sdk does.

Grade a run Vally did not start

vally grade reads an ATIF file (Agent Trajectory Interchange Format) on standard input. schema_version must start with ATIF-. Each kind of grader needs one input: Lesson 25

npm install --prefix app
sh app/run.sh claude-haiku-4.5
node app/traces-to-atif.mjs app-run/traces.jsonl \
  > app-run/trajectory.json
vally grade -e evals/release.eval.yaml \
  --stimulus since-last-release \
  --workspace app-run/repo \
  --diff-file app-run/change.diff \
  --verbose < app-run/trajectory.json

Three gaps: Vally's cost stays empty (the steps' cost_usd is kept but not added up); wall time is 0; a skill counts as loaded only if the trajectory shows a call to the skill tool.

Trace files hold private values

With content captured, a trace holds the whole prompt, every file the agent read, full paths on your machine, and enduser.pseudo.id, which identifies your account. Clean them before attaching or committing them.

Let Vally run the app

An executor plugin is a JavaScript module that exports registerExecutors. Each executor has a name, an execute function that runs one trial and returns a trajectory, and shutdown. Vally still prepares the workspace, runs commands:, saves the patch and grades. Lesson 26

import { randomUUID } from "node:crypto";
import { computeMetrics } from "@microsoft/vally";

const releaseApp = {
  name: "release-app",
  async execute(stimulus, options) {
    const startedAt = new Date();
    const { reply, events } = await writeEntries({
      repoDir: options.workDir,
      model: options.model,

    });
    const completedAt = new Date();
    const trajectoryEvents = toTrajectoryEvents(events);
    return {
      id: randomUUID(),
      stimulus,
      events: trajectoryEvents,
      output: reply,
      workDir: options.workDir,
      metrics: {
        ...computeMetrics(trajectoryEvents),
        wallTimeMs: completedAt - startedAt,
      },
      metadata: { model: options.model,
        executor: "release-app", /* … */ },
    };
  },
  async shutdown() {},
};

export function registerExecutors(registry) {
  registry.register(releaseApp);
}

writeEntries is the app's own function, and toTrajectoryEvents is the mapping below; the full execute, imports and metadata are in lesson 26 and practice-starter/app/vally-executor.mjs. computeMetrics adds up tokens, cost, tool calls by name, skills loaded and turns, as the built-in executor does. Load the plugin in .vally.yaml, then select it per run with --executor release-app, per eval file with defaults.executor, or per experiment with executor under overrides.

plugins:
  executor:
    - ./app/vally-executor.mjs
vally eval -e evals/release.eval.yaml \
  --executor release-app \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --workers 2 --output-dir results/lesson-26

Ours declares no simulation support, so a stimulus with a simulation block ends in ERROR before any agent starts (troubleshooting).

Joining the app's traces to Vally's

Vally writes a vally.trial span and a vally.attempt span per attempt to otel-spans.jsonl in the run folder. Hand options.traceContext to the SDK and the app's invoke_agent span becomes a child of the attempt span, in the same trace. Lesson 26

const client = new CopilotClient({
  telemetry: options.telemetry,
  onGetTraceContext: () => options.traceContext ?? {},
});

Check: the session span in executor-artifacts/app-traces.jsonl has the trial's traceId, and its parentSpanId is the vally.attempt span's spanId. Without a trace context (the app run from run.sh), invoke_agent is the root of its own trace.
