Workflow guide: improving a skill with evals

Verified 2026-11-10 · Vally 0.21.0

This guide takes a skill from "it worked when I tried it" to a quick suite and a full suite you can run after every change, with a known cost per passing trial and a check that fails on a regression. A last stage covers a skill that an app calls. It is written for someone who took the course a while ago. Every step says what to do, how to tell it is done, and which lesson explains it. The commands use the course's file names; put your own in their place.

Where are you?

  • Starting with a new skill and no evals: start at A.
  • You have an eval file and want graders: GOTO C1.
  • You wrote or changed a grader: GOTO C3.
  • You edited the skill: GOTO H2.
  • A count improved and you want to know if it is real: GOTO F1.
  • You are about to rely on an edit: GOTO F4.
  • You need to know what the skill costs, or want budgets: GOTO G1.
  • A model you use was replaced: GOTO G4.
  • A run ended in ERROR, FLAKY or a surprising FAIL: GOTO I1.
  • The skill is called by an app: GOTO J1.

The workflow

  1. ASet up
    1. A1Check the tools. 
      node --version
vally --version
      Done when: Node is 22.15 or higher and Vally prints a version. If either is missing, see Before you start on the course home. Lesson 1
    2. A2Lay out the folder: skills/your-skill/SKILL.md, and evals/ beside skills/, never inside it. Put starting files under evals/fixtures/. Done when: no eval file or grading file is inside a skill folder. Lesson 6
    3. A3List your account's models and choose two that differ. 
      vally eval -e evals/one-request.eval.yaml \
  --model list-my-models \
  --output-dir results/models
      Done when: the error lists your models and you have written down two. Lesson 1
  2. BSee what the skill does
    1. B1Write an eval file with four to six realistic requests and no graders. Include messy ones. Lint it. 
      vally lint -e evals/six-requests.eval.yaml
      Done when: lint reports the file is valid. Lesson 4
    2. B2Run it on both models without grading. 
      vally eval -e evals/six-requests.eval.yaml \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --skip-grade --workers 2 \
  --output-dir results/reading
      Done when: every trial finished. If any trial shows ERROR, it did not complete: GOTO I2. Lesson 4
    3. B3Read every workspace.patch. Write one note per trial, then group the notes into named failure modes. Done when: each failure mode has a name and a trial that shows it. If you found none, write harder requests and GOTO B1. Lesson 4
  3. CTurn failures into graders you can trust
    1. C1For each failure mode, choose the cheapest grader that can decide it. If it is about what was added or not added, use a diff grader and continue to C2. If it is about where something sits in a file, use a script through the grading environment and continue to C2. If only a reader could decide it, GOTO E1. Lesson 5
    2. C2Add the graders, one per failure mode, named after it. Lint. 
      vally lint -e evals/changelog.eval.yaml
      Done when: lint shows no errors. One warning, scoring-defaults-applied, is expected. Lesson 5
    3. C3Save a correct trial's patch as the golden patch, name it in the stimulus, and run the oracle both ways. 
      vally oracle -e evals/changelog.eval.yaml --verbose
      vally oracle -e evals/changelog.eval.yaml \
  --no-golden-input --verbose
      Done when: the first prints PASSED for each stimulus that has a golden patch and the second ends each stimulus with baseline OK. If a grader is "trivially passing" or fails the golden patch, fix it and GOTO C2. Lesson 7
    4. C4For every grader the oracle marked N/A, re-grade a saved run where that failure happened. Type this in the run's folder. 
      vally grade -e ../../../evals/changelog.eval.yaml \
  --run-dir . < results.jsonl
      Done when: the grader fails the trials you know are bad. If it passes them, the grader cannot fail. Fix it and GOTO C2. If no saved run has diffs yet, continue to D1 and come back after it. Ignore script graders here: with the workspace gone they fail every trial, and with --require-pass they make the exit code 1. C3 is their test. Lesson 8
  4. DMeasure, edit, measure
    1. D1Run the graded eval several times on both models and write down the count per stimulus and model. 
      vally eval -e evals/changelog.eval.yaml \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --runs 3 --workers 2 \
  --output-dir results/before
      Done when: you have a count for each stimulus on each model. If any trial shows ERROR, it did not complete: GOTO I2. Lesson 5
    2. D2Add one rule to the skill per failure mode. Say what to do in the case the skill left open. Done when: each rule names a case and an action. Lesson 5
    3. D3Run D1's command again into a new folder, and compare stimulus by stimulus. If a count moved only a little, GOTO F1 before believing it. If a stimulus that passed now fails, read its patch before changing anything. Lesson 5
    4. D4Test loading: requests that should load the skill, near-miss requests that should not, and neighbouring skills installed. Rewrite the description if it misses. Done when: the skill loads for every request that needs it and for no near-miss. If any trial shows ERROR, it did not complete: GOTO I2. Lesson 9
    5. D5Compare with no skill. 
      vally experiment run \
  evals/with-and-without.experiment.yaml \
  --workers 2 --output-dir results/with-and-without
      Done when: you can say on which stimuli the skill helps, makes no difference, or hurts. If a stimulus passes without the skill and fails with it, find the rule that causes it and GOTO D2. Lesson 10
    6. D6Write one conversation of three requests, each leaning on a different rule, with a grader per turn. Done when: each turn's own change is graded. Lesson 11
  5. EJudge what code cannot
    1. E1Produce a dozen or more entries, read each, and write your own yes or no. Done when: every entry has your label, written before any judge ran. Lesson 12
    2. E2Add a rubric with one criterion, a prompt grader with scoring: binary, and a named judge_model. Lint. Lesson 12
    3. E3Judge the saved trials. Typed in the run's folder. 
      vally grade -e ../../../evals/wording.eval.yaml \
  --run-dir . --verbose < results.jsonl
      Done when: each trial has a verdict and a reason. Lesson 12
    4. E4Count the four boxes and work out TPR and TNR. Done when: you have both numbers and the number of labels. If either is below 90%, read each disagreement, reword the criterion, and GOTO E3. Stop after two attempts and add labels. Lesson 13
  6. FDecide whether a change is real
    1. F1Keep a copy of the skill as it was. If an older copy is there from a previous comparison, remove it first, because cp -R would put the new copy inside it. 
      rm -rf skills/changelog-entry-before
      cp -R skills/changelog-entry \
  skills/changelog-entry-before
      Lesson 15
    2. F2Run both versions on both models as variants of one experiment, three trials or more each. 
      vally experiment run \
  evals/before-and-after.experiment.yaml \
  --workers 2 --output-dir results/before-and-after
      Done when: you have trials passed, of trials finished, for each variant. Lesson 15
    3. F3Put the before and after counts into the range calculator on the judges and small counts sheet. If the ranges do not overlap, the change is real. Continue to F4. If they overlap, say "these trials cannot tell". Run more trials or use harder requests, and GOTO F2. Lesson 15
    4. F4Before relying on an edit (not after every edit), judge before against after side by side, once per model. Type this in the run folder F2 made, naming its variant folders. 
      vally compare \
  --baseline haiku-before \
  --treatment haiku-after \
  --judge-model claude-sonnet-5.5 \
  --fail-on-regression
      echo $?
      Done when: it prints 0 for every model. It exits 1 only when the after version's mean score is below zero and its whole range is too. If it prints 1, read the pairs the after version lost, then GOTO D2. This gates judged quality only: a rise in tokens does not change the exit code. Gate cost with budgets: GOTO G5. Lesson 19
  7. GPrice it and set ceilings
    1. G1Run an experiment whose variants differ in model and reasoning effort (vary: [/defaults/model, /defaults/reasoning_effort]), three trials each. 
      vally experiment run \
  evals/cost.experiment.yaml \
  --workers 2 --output-dir results/cost
      Done when: you have each variant's cost per passing trial, its total cost divided by its passing trials, from the cost calculator in lesson 16. Judge calls are not in Vally's cost. Lesson 16
    2. G2Choose a variant. Drop any that another beats on both counts: costs more and passes no more often. Among the rest, choose by what a failure costs you. Tokens are not price: in our run the model with the fewest tokens cost the most. Done when: you can state the choice with its pass rate and cost per passing trial. Lesson 16
    3. G3Does the app call its model through its own provider? If no, continue to G4. If yes, add a variant with executor: {name: copilot-sdk, config: {provider: …}}, keep keys out of the file, and add /defaults/executor to vary. A model on your own computer needs --workers 1. Done when: the variant runs. Its cost is empty: price its tokens at your provider's rate. If the dry run says Experiment drift detected, a path is missing from vary. Lesson 17
    4. G4Before moving the suites to another model, repeat G1 with it, then re-test the budgets on its trials as in G5, then run the full suite at H3. Done when: the new model's cost per passing trial is known and its good trials pass every budget. Lesson 21
    5. G5Put budget graders on the quick stimuli, each max just above a typical saved trial, and a time limit that stops the agent. 
            - type: token-budget
        config:
          max: 107000
      - type: turn-count
        config:
          max: 5
      - type: wall-time
        config:
          max: 14s
          constraints:
      max_agent_duration: 1m
      Then test them on saved trials, for free, in a run's folder: 
      vally grade -e ../../../evals/changelog.eval.yaml \
  --run-dir . < results.jsonl
      Done when: every good saved trial passes every budget. If a good trial fails one, raise that max and re-grade. A token budget catches a trial that loops. It does not stop an expensive model; G1 does. Lesson 18
  8. HKeep it working
    1. H1Tag the stimuli that code can check, and define a quick and a full suite in .vally.yaml. The quick stimuli carry the budgets from G5. Lesson 21
    2. H2After every edit to the skill, run the quick suite. 
      vally eval --suite quick \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --workers 2 --require-pass \
  --output-dir results/quick
      Done when: the command exits with 0. An over-budget trial fails like any other. If any trial shows ERROR, it did not complete: GOTO I2. If it fails, read the failing trial's patch, then GOTO D2. Lesson 21
    3. H3Before sharing the skill, and when a model changes (after G4), run the full suite and repeat D5. 
      vally eval --suite full \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --workers 2 --require-pass \
  --output-dir results/full
      Done when: every eval passes on every model you support. If any trial shows ERROR, it did not complete: GOTO I2. Lesson 21
    4. H4Write or update the one-page conventions file. Done when: a teammate could run H2 and H3 from it. Lesson 21
    5. H5Optional: run the quick suite automatically on a hosting service. We have not run this step. It follows Vally's Add to CI page, which gives the full workflow file. The lines that matter: 
      permissions:
  contents: read
  copilot-requests: write
      env:
  GITHUB_TOKEN: ${{ github.token }}
      Done when: a change that breaks a quick stimulus makes the automated check fail.
  9. IWhen a run goes wrong
    1. I1Is the eval valid? Lint it, and read the run's first lines. 
      vally lint -e evals/changelog.eval.yaml
      Done when: lint says the file is valid and the run reached an agent. If lint passes but every trial ends in ERROR within milliseconds, quote each commands: entry; see the troubleshooting sheet. Lesson 20
    2. I2Did it complete? Read the ERROR line, then list the trial's folder. If it holds only metadata.json, setup failed: fix the eval file and GOTO I4. If it holds events.jsonl and no workspace.patch, the agent was stopped: a time limit or a dropped session. Fix and GOTO I4. If it holds both, the agent finished: GOTO I3. Done when: you know where the trial stopped. The troubleshooting sheet lists the messages. Lesson 20
    3. I3Why was the result unexpected? Read the grader's evidence and the trial's workspace.patch; add --verbose to vally eval to see the agent's final reply. Decide who is wrong. If the grader is wrong, fix it and GOTO I4. If the agent is wrong, it is a real failure: GOTO D2. If the stimulus is FLAKY, more trials before deciding: GOTO F2. Lesson 20
    4. I4Does the fix work? Use the cheapest check that can show it. A fix to a diff grader, a budget or a rubric: re-grade the saved run, as in C4, free or judge calls only. A fix to a file or script grader: vally oracle. A fix to the setup or a time limit: one new run, on one model. Done when: the symptom is gone. If it is still there after two attempts, GOTO I1 and question each answer again. Lesson 20
  10. JA skill inside an app
    1. J1Start the agent where the app would: stage the files the app's checkout has, and run the app's setup step as commands:, each entry quoted. Lint and run. Done when: the patches show only the agent's change, not what setup created. Lesson 22
    2. J2Add the app's own test as a hidden run-command grader, staged through grading_environment, and run the oracle without the golden patch. 
      vally oracle -e evals/release.eval.yaml \
  --no-golden-input
      Done when: the test fails the unchanged workspace. Lesson 22
    3. J3Only for steps the app depends on, add tool-calls graders (required or disallowed), max-repeat and skill-invocation. Re-grade a saved run, for free. Done when: each route grader fails a saved trial that broke its rule, or you know none did. Lesson 23
    4. J4For a tool the app relies on, add a tagged stimulus whose simulation block makes the tool fail, take the answer out of the workspace, and run only it. 
      vally eval -e evals/release.eval.yaml \
  --tag case=tool-fails \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --runs 3 --workers 2 \
  --output-dir results/tool-fails
      Done when: the trials show whether the agent writes nothing, says why, and stops retrying. Lesson 24
    5. J5Decide where to grade the app. To check its real runs, continue to J6. To count trials of the app's own code on several models, GOTO J7. Most teams do both. Lesson 25
    6. J6Grade a run Vally did not start: convert the app's traces to ATIF, then grade with the diff and the workspace. 
      node app/traces-to-atif.mjs app-run/traces.jsonl \
  > app-run/trajectory.json
      vally grade -e evals/release.eval.yaml \
  --stimulus since-last-release \
  --workspace app-run/repo \
  --diff-file app-run/change.diff \
  --verbose < app-run/trajectory.json
      Done when: there is one line per grader. Cost is empty and wall time 0 for this input. Lesson 25
    7. J7Let Vally run the app: write the executor plugin's execute, list the plugin under plugins: executor: in .vally.yaml, and select it. 
      vally eval -e evals/release.eval.yaml \
  --executor release-app \
  --model claude-haiku-4.5,gpt-5.6-terra \
  --workers 2 --output-dir results/app
      Done when: eval-results.md says Executor: release-app under each table. Stimuli with a simulation block end in ERROR at no cost; that is expected. To compare models through the app, set executor under an experiment's overrides and GOTO G1. Lesson 26
